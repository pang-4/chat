# k6 WebSocket 동시 연결 부하 테스트

## 실습 목표

Smoke Test로 WebSocket 기능이 정상적으로 동작하는 것을 확인한 후, 여러 가상 사용자가 동시에 연결을 유지하고 채팅을 보내는 상황을 테스트한다.

```text
Mac
└── k6 가상 사용자 여러 명
        ↓ WebSocket 연결과 채팅 전송
Ubuntu 미니 PC
├── Go 채팅 서버
└── PostgreSQL
```

이번 테스트는 서버의 최대 한계를 확정하는 테스트가 아니다. 동시 연결 부하가 정상적으로 발생하는지 확인하는 예비 부하 테스트다.

---

## Smoke Test와 Load Test 차이

| 구분 | 파일 | 목적 |
|---|---|---|
| Smoke Test | `websocket-smoke.js` | 사용자 한 명으로 연결과 채팅 기능 확인 |
| Load Test | `websocket-load.js` | 여러 사용자의 동시 연결과 반복 메시지 처리 확인 |

Smoke Test는 기능이 정상인지 빠르게 검사하고, Load Test는 동시 사용자가 증가했을 때도 정상적으로 처리하는지 검사한다.

---

## 테스트 파일

```text
loadtest/websocket-load.js
```

테스트의 기본 설정은 다음과 같다.

```text
VUS=10
HOLD_SECONDS=15
MESSAGE_INTERVAL_MS=1000
```

| 설정 | 의미 |
|---|---|
| `VUS` | 동시에 실행할 가상 사용자 수 |
| `HOLD_SECONDS` | WebSocket 연결을 유지할 시간 |
| `MESSAGE_INTERVAL_MS` | 각 사용자가 메시지를 전송하는 간격 |

각 가상 사용자는 다음 순서로 동작한다.

```text
WebSocket 연결
→ 입장 메시지 전송
→ 입장 Broadcast 확인
→ 일정 간격으로 채팅 전송
→ 자기 채팅 Broadcast와 DB ID 확인
→ 보낸 자기 메시지를 모두 받았는지 확인
→ 연결 종료
```

---

## Threshold

Threshold는 테스트의 합격과 실패를 판단하는 기준이다.

```javascript
thresholds: {
  checks: ['rate>0.99'],
  connection_success: ['rate>0.99'],
  message_delivery_success: ['rate>0.99'],
  ws_connecting: ['p(95)<500'],
}
```

| 기준 | 의미 |
|---|---|
| `checks rate>0.99` | 전체 기능 검사의 99% 초과 성공 |
| `connection_success rate>0.99` | WebSocket 연결의 99% 초과 성공 |
| `message_delivery_success rate>0.99` | 자기 메시지 전체 수신의 99% 초과 성공 |
| `ws_connecting p(95)<500` | WebSocket 연결의 95%가 500ms 미만 |

## 10명 동시 연결 테스트

### 실행 명령

`loadtest` 폴더 안에서 실행하였다.

```bash
k6 run \
  -e WS_URL=ws://100.126.215.15:8080/ws \
  websocket-load.js
```

기본값을 사용하여 가상 사용자 10명이 약 15초 동안 연결을 유지하고, 각 사용자가 1초 간격으로 메시지를 전송하였다.

### 결과

```text
동시 사용자: 10명
연결 성공: 10/10, 100%
메시지 전달 성공: 10/10, 100%
검사 성공: 300/300
검사 실패: 0

WebSocket 연결 p95: 81.27ms
자기 메시지 지연 평균: 42.87ms
자기 메시지 지연 p95: 79ms
자기 메시지 최대 지연: 80ms

WebSocket 수신 메시지: 1,500개
WebSocket 송신 메시지: 160개
수신 데이터: 189kB
송신 데이터: 12kB
```

이번 결과를 통해 가상 사용자 10명이 동시에 연결된 상태에서 연결 실패와 자기 메시지 손실 없이 채팅을 처리한 것을 확인하였다.

## 50명 동시 연결 테스트

### 실행 명령

```bash
k6 run \
  -e WS_URL=ws://100.126.215.15:8080/ws \
  -e VUS=50 \
  -e HOLD_SECONDS=60 \
  websocket-load.js
```

가상 사용자 50명이 약 60초 동안 연결을 유지하고, 각 사용자가 1초 간격으로 메시지를 전송하였다.

### 결과

```text
동시 사용자: 50명
연결 성공: 50/50, 100%
메시지 전달 성공: 50/50, 100%
검사 성공: 6,000/6,000
검사 실패: 0

WebSocket 연결 p95: 24.42ms
자기 메시지 지연 평균: 41.48ms
자기 메시지 지연 p90: 69ms
자기 메시지 지연 p95: 88.54ms
자기 메시지 최대 지연: 324ms

WebSocket 수신 메시지: 150,548개
WebSocket 송신 메시지: 3,050개
수신 데이터: 20MB
송신 데이터: 216kB
```

50명 테스트에서도 연결과 메시지 전달 성공률이 100%였으며, 전체 검사 6,000건이 모두 성공하였다.

10명 테스트의 자기 메시지 지연 p95는 약 79ms이고, 50명 테스트에서는 약 88.54ms로 측정되었다. 사용자가 증가하면서 p95가 조금 증가했지만 현재 테스트에서는 메시지 손실이나 서버 중단이 발생하지 않았다.

## Broadcast로 수신량이 커지는 이유

현재 채팅 서버는 사용자가 보낸 메시지를 연결된 모든 사용자에게 Broadcast한다.

```text
사용자 1명이 메시지 1개 전송
→ 연결된 50명이 각각 수신
```

따라서 전송 메시지 수보다 수신 메시지 수가 훨씬 크게 측정된다.

```text
약 2,950개의 채팅 × 사용자 50명
≈ 약 147,500회의 채팅 수신
```

여기에 사용자 입장과 퇴장 시스템 메시지 등이 포함되어 전체 수신 메시지가 150,548개로 측정되었다.

사용자 수가 증가하면 Broadcast 전달 작업은 빠르게 증가한다.

```text
사용자 N명이 각각 메시지를 전송
→ 대략 N × N 형태로 전달량 증가
```

## PostgreSQL CPU가 증가한 이유

채팅 서버는 채팅 메시지를 받을 때마다 PostgreSQL에 저장한 뒤 Broadcast한다.

```text
채팅 수신
→ PostgreSQL INSERT
→ WAL과 데이터 기록
→ 생성된 메시지 ID 반환
→ WebSocket Broadcast
```

50명 테스트에서는 약 60초 동안 약 2,950개의 채팅이 발생하였다.

```text
약 2,950개 ÷ 60초
≈ 초당 49개의 DB 저장 요청
```

따라서 테스트가 실행되는 동안 PostgreSQL CPU 사용량이 증가하고, 테스트 종료 후 다시 내려가는 것은 정상적인 동작이다.

`docker stats`는 현재 순간의 상태만 보여주므로 테스트가 끝난 후 과거의 CPU 변화를 다시 확인할 수 없다. 이후 Prometheus와 Grafana를 구성한 뒤 동일한 테스트를 다시 실행하여 CPU, 메모리, 지연시간을 시간별 그래프로 기록한다.

## 테스트 결과 정리

```text
10명 테스트
→ 연결 및 메시지 전달 성공률 100%

50명 테스트
→ 연결 및 메시지 전달 성공률 100%
→ 약 15만 건의 WebSocket 수신 처리
→ 자기 메시지 지연 p95 약 88.54ms
```

현재 결과는 단일 Docker Compose 채팅 서버가 50명의 예비 부하 테스트를 정상 처리했다는 의미다. 서버의 최대 처리 한계나 대규모 운영 성능을 증명한 결과는 아니다.

정식 성능 비교는 Kubernetes와 Redis, Prometheus와 Grafana 구성이 끝난 후 다시 수행한다.

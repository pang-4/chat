## Ingress란

Ingress는 Kubernetes Cluster 외부에서 들어온 HTTP와 HTTPS 요청을 내부 Service로 전달하기 위한 Routing 규칙이다.

```text
외부 Client
    ↓
Ingress Controller
    ↓ Ingress Rule 확인
Kubernetes Service
    ↓
Pod
```

Ingress Resource 자체가 Network Traffic을 처리하는 Proxy Process는 아니다.

```text
Ingress Resource
= 어느 Host와 Path를 어느 Service로 보낼지 정의한 규칙

Ingress Controller
= 그 규칙을 읽고 실제 Traffic을 전달하는 Process
```

현재 프로젝트에서는 NGINX Ingress Controller를 사용한다.

---

## Service와 Ingress의 차이

### Service

Service는 여러 Pod 앞에서 안정적인 내부 주소와 Port를 제공한다.

현재 Chat Service:

```yaml
kind: Service
metadata:
  name: chat-app
spec:
  type: ClusterIP
  selector:
    app: chat-app
  ports:
    - name: http
      port: 8080
      targetPort: http
```

역할:

```text
chat-app Service:8080
    ├── Chat Pod 1:8080
    ├── Chat Pod 2:8080
    └── Chat Pod 3~6:8080
```

`ClusterIP`이므로 기본적으로 Cluster 내부에서 사용한다.

### Ingress

Ingress는 외부 HTTP 요청의 Host와 Path를 보고 적절한 Service로 전달한다.

현재 Chat Ingress:

```yaml
kind: Ingress
metadata:
  name: chat-app
spec:
  ingressClassName: nginx
  rules:
    - http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: chat-app
                port:
                  name: http
```

현재는 `/`로 들어오는 모든 요청을 `chat-app` Service의 `http` Port로 전달한다.

```text
/ws
/health/live
/health/ready
/metrics
/stats
    ↓
chat-app Service
```

## Ingress Controller

Ingress Controller는 Ingress Resource를 감시하고 실제 Reverse Proxy 설정을 만든다.

Minikube Addon으로 설치하였다.

```bash
minikube addons enable ingress
```

상태 확인:

```bash
kubectl get pods -n ingress-nginx
kubectl get svc ingress-nginx-controller -n ingress-nginx
```

현재 Service:

```text
NAME                       TYPE       PORT(S)
ingress-nginx-controller   NodePort   80:31673/TCP,443:30866/TCP
```

의미:

```text
HTTP:
Minikube Node 31673
→ Ingress Controller 80

HTTPS:
Minikube Node 30866
→ Ingress Controller 443
```

## WebSocket과 Ingress

WebSocket은 처음에는 HTTP 요청으로 시작한다.

```text
Client
→ HTTP GET /ws
→ Upgrade: websocket
→ 101 Switching Protocols
→ 장시간 TCP Connection 유지
```

NGINX Ingress가 Upgrade Header를 처리하여 Backend Chat Pod와 WebSocket Connection을 만든다.

현재 Annotation:

```yaml
nginx.ingress.kubernetes.io/proxy-read-timeout: "3600"
nginx.ingress.kubernetes.io/proxy-send-timeout: "3600"
nginx.ingress.kubernetes.io/proxy-buffering: "off"
```

| Annotation | 의미 |
|---|---|
| `proxy-read-timeout` | Backend에서 데이터를 기다릴 수 있는 시간 |
| `proxy-send-timeout` | Backend로 데이터를 보낼 때의 Timeout |
| `proxy-buffering: off` | 장기 실시간 연결에서 Proxy Buffering 비활성화 |

WebSocket Connection이 한 번 특정 Pod에 연결되면 그 Connection은 종료될 때까지 같은 Pod와 유지된다.

HPA가 새 Pod를 만들더라도 기존 Connection은 새 Pod로 이동하지 않는다. 새로 만들어지는 Connection부터 새 Backend Pod로 분산된다.

## 두 Port Forward 명령의 차이

### Chat Service 직접 Port Forward

```bash
kubectl port-forward \
  --address=100.126.215.15 \
  service/chat-app \
  8080:8080 \
  -n chat
```

경로:

```text
Mac
→ Mini PC Tailscale IP:8080
→ kubectl port-forward
→ 선택된 Chat Pod:8080
```

`kubectl port-forward service/chat-app`은 Service의 외부 Load Balancer를 그대로 노출하는 방식이 아니다.

Service가 선택하는 Endpoint 중 하나의 Pod를 찾아 그 Pod에 Port Forward Session을 연결한다.

따라서 이 경로에서는 WebSocket Connection이 특정 Chat Pod 하나에 집중된다.

검증 용도:

- Chat Application에 직접 연결되는가
- WebSocket 기능이 동작하는가
- PostgreSQL 저장이 되는가
- Redis Publish와 Subscribe가 되는가
- 단일 Pod가 어느 정도 부하를 처리하는가

검증하지 못하는 것:

- Ingress WebSocket Upgrade
- Ingress Routing
- Chat Pod 여러 개로 Connection 분산

### Ingress Controller Port Forward

```bash
kubectl port-forward \
  --address=100.126.215.15 \
  service/ingress-nginx-controller \
  8080:80 \
  -n ingress-nginx
```

경로:

```text
Mac
→ Mini PC Tailscale IP:8080
→ kubectl port-forward
→ NGINX Ingress Controller:80
→ Ingress Rule
→ chat-app Service:8080
→ Chat Pod
```

Port Forward Session 자체는 Ingress Controller Pod 하나에 연결된다.

하지만 그 뒤에서 NGINX가 Ingress Rule을 적용하고 `chat-app` Service의 Backend Endpoint로 신규 Connection을 전달하므로 Chat Pod 분산을 확인할 수 있다.

검증 용도:

- NGINX Ingress를 통한 WebSocket Upgrade
- Ingress Path Routing
- Ingress 뒤 Chat Service 접근
- 신규 WebSocket Connection의 Pod 분산

### 비교

| 항목 | `service/chat-app` | `service/ingress-nginx-controller` |
|---|---|---|
| Port Forward 대상 | Chat Pod | Ingress Controller Pod |
| Ingress 통과 | X | O |
| Ingress Rule 검증 | X | O |
| WebSocket Upgrade 검증 | Chat App만 검증 | NGINX 포함 검증 |
| 여러 Chat Pod 분산 | X, 한 Pod에 집중 | O, Ingress 뒤 Service에서 분산 |
| 주요 용도 | Application 직접 점검 | Ingress 통합 점검 |

두 명령 모두 `kubectl port-forward`를 사용하는 임시 개발 경로이므로 대규모 부하 테스트의 정식 외부 진입점으로 사용하기에는 한계가 있다.

## 실습에서 접속 경로가 바뀐 과정

### 1단계: Chat Service 직접 연결

초기 10명과 50명 테스트:

```text
Mac k6
→ service/chat-app Port Forward
→ 특정 Chat Pod
```

확인한 내용:

- WebSocket Connection과 Message 전달 성공
- PostgreSQL 저장
- Redis Pub/Sub
- Prometheus와 Grafana Metric
- 단일 Pod 부하

Grafana에서 특정 Chat Pod의 Memory와 Network가 다른 Pod보다 크게 증가하여 한 Pod에 Connection이 집중된 것을 확인하였다.

### 2단계: Ingress를 통한 분산

50명과 200명 분산 테스트:

```text
Mac k6
→ service/ingress-nginx-controller Port Forward
→ NGINX Ingress
→ chat-app Service
→ Chat Pod 3개
```

결과:

```text
50명:  19 / 14 / 17
200명: 68 / 66 / 66
```

신규 WebSocket Connection이 여러 Chat Pod로 분산되는 것을 확인하였다.

### 3단계: 300명 Port Forward 한계 확인

300명 HPA 테스트에서 약 1.7GB의 Broadcast 데이터를 전달하던 중 다음 오류가 발생하였다.

```text
write: broken pipe
error: lost connection to pod
```

Chat Pod와 HPA는 동작했지만 `kubectl port-forward`가 끊기면서 모든 WebSocket Connection이 종료되었다.

따라서 대규모 테스트에서는 Port Forward를 제거하였다.

### 4단계: Ingress NodePort 직접 사용

Ingress Controller Service가 이미 NodePort로 노출되어 있었다.

```bash
kubectl get svc ingress-nginx-controller \
  -n ingress-nginx \
  -o wide

minikube ip
```

결과:

```text
Minikube IP: 192.168.49.2
HTTP NodePort: 31673
```

Mini PC 내부 확인:

```bash
curl --max-time 5 \
  http://192.168.49.2:31673/health/live
```

결과:

```text
ok
```

Minikube IP는 Docker 내부 Network이므로 Mac에서 직접 접근하기 어렵다.

Mini PC에서 `socat`으로 Tailscale 주소와 NodePort를 연결하였다.

```bash
socat \
  TCP-LISTEN:8080,bind=100.126.215.15,reuseaddr,fork \
  TCP:192.168.49.2:31673
```

최종 경로:

```text
Mac k6
→ 100.126.215.15:8080
→ socat
→ 192.168.49.2:31673
→ NGINX Ingress Controller
→ Ingress Rule
→ chat-app Service
→ Chat Pod 3~6개
```

이 경로로 10명 사전 검증 후 300명 HPA 테스트를 완료하였다.

```text
Connection: 300/300
Message 전달: 300/300
Check: 225,290/225,290
HPA: 3 → 6 → 4 → 3
Packet Drop: 0
```

## 자주 혼동하는 부분

### Ingress가 Pod를 직접 생성하는가

아니다. Pod는 Deployment와 ReplicaSet이 생성한다.

Ingress는 외부 요청을 Service로 보내는 Routing 규칙이다.

### Ingress가 HPA를 실행하는가

아니다. HPA는 Metrics Server의 CPU Metric을 보고 Deployment Replica 수를 변경한다.

Ingress와 Service는 새로 들어오는 Connection을 준비된 Pod로 전달한다.

### Service Port Forward면 Service Load Balancing을 검증한 것인가

아니다. `kubectl port-forward service/...`는 선택된 Pod 하나로 Session을 연결하므로 정식 Service Load Balancer 경로와 다르다.

### Ingress Controller Port Forward는 운영 방식인가

아니다. Ingress Routing을 간단히 확인하는 개발·실습 방식이다.

운영 환경에서는 다음 구성이 필요하다.

```text
Public 또는 Private LoadBalancer
→ Ingress Controller
→ DNS
→ TLS 인증서
→ Kubernetes Service
```

## 핵심 정리

```text
Service는 Pod 앞의 안정적인 내부 주소다.
Ingress는 외부 HTTP·HTTPS 요청을 Service로 보내는 규칙이다.
Ingress Controller는 그 규칙을 실제로 실행하는 Proxy다.
service/chat-app Port Forward는 특정 Chat Pod 직접 점검에 사용했다.
service/ingress-nginx-controller Port Forward는 Ingress와 Pod 분산 확인에 사용했다.
300명 부하에서는 Port Forward가 끊겨 socat과 Ingress NodePort 경로로 변경했다.
최종 300명 테스트에서 Message 전달, HPA 확장·축소와 Packet Drop 0을 확인했다.
```

# Grafana란 무엇이고 왜 사용하는가

## Grafana란

Grafana는 여러 Data Source의 데이터를 Query하고 Dashboard로 시각화하는 Observability 도구다.

현재 프로젝트에서는 Prometheus가 수집한 Kubernetes와 채팅 서버 Metric을 Grafana에서 그래프와 표로 확인한다.

```text
Chat Application /metrics
Kubernetes kubelet·cAdvisor
kube-state-metrics
node-exporter
        ↓
    Prometheus
  수집·저장·Query
        ↓
     Grafana
 Dashboard·시각화
```

Grafana가 직접 CPU와 Memory를 측정하는 것은 아니다.

Prometheus가 Metric을 수집하고 저장하며, Grafana는 PromQL로 Prometheus를 조회하여 사람이 이해하기 쉬운 화면으로 표현한다.

---

## Grafana를 사용하는 이유

### 현재 상태를 한 화면에서 확인

Terminal에서 다음 명령으로 현재 자원 사용량을 확인할 수 있다.

```bash
kubectl top pods -n chat
```

하지만 이 명령은 현재 순간의 값만 보여준다. Grafana에서는 CPU, Memory, Network 등의 변화를 시간 그래프로 확인할 수 있다.

### 과거 시점과 장애 전후 비교

장애가 발생한 뒤에도 이전 데이터를 확인할 수 있다.

```text
CPU가 언제부터 증가했는가
Memory가 지속적으로 증가했는가
Pod가 언제 재시작되었는가
Network Traffic이 언제 급증했는가
```

### 여러 Component를 함께 비교

현재 `chat` Namespace에는 다음 Workload가 있다.

```text
chat-app 3개
postgres 1개
redis 1개
```

Grafana에서 이들의 CPU, Memory, Network를 같은 시간 범위로 비교하면 어느 Component가 병목인지 판단하기 쉽다.

### Application Metric 확인

Kubernetes 자원 Metric뿐 아니라 애플리케이션이 직접 제공하는 Metric도 확인할 수 있다.

현재 채팅 서버는 다음 Metric을 제공한다.

```text
chat_websocket_connections
```

PromQL:

```promql
sum(chat_websocket_connections)
```

이 값은 전체 Chat Pod에 연결된 활성 WebSocket 연결 수다. 고유 사용자 수가 아니라 연결 수이므로 한 사용자가 여러 Tab을 열면 여러 개로 계산될 수 있다.

### Alert 기준으로 활용

Dashboard 확인에서 더 나아가 다음 조건으로 Alert을 만들 수 있다.

```text
CPU 사용률이 일정 시간 80% 이상
Memory가 Limit에 근접
Pod 재시작 횟수 증가
Packet Drop 발생
Application Error 증가
```

## Metrics Server, Prometheus, Grafana 차이

| Component | 역할 |
|---|---|
| Metrics Server | 현재 CPU·Memory를 Metrics API로 제공 |
| Prometheus | Metric을 주기적으로 수집하고 시계열로 저장 |
| Grafana | Prometheus 데이터를 Query하고 Dashboard로 시각화 |

Metrics Server는 다음 명령과 HPA에 사용된다.

```bash
kubectl top nodes
kubectl top pods
```

Prometheus와 Grafana는 시간에 따른 변화와 과거 데이터를 분석할 때 사용한다.

세 Component는 서로 대체 관계가 아니라 목적이 다르다.

## kube-prometheus-stack

이 프로젝트에서는 Helm Chart인 `kube-prometheus-stack`을 사용하였다.

이 Chart를 설치하면 다음 Monitoring Component를 함께 구성할 수 있다.

- Prometheus Operator
- Prometheus
- Alertmanager
- Grafana
- kube-state-metrics
- node-exporter
- Kubernetes 기본 Dashboard와 Alert Rule
- ServiceMonitor Custom Resource Definition

현재 설치 정보:

```text
Helm Release: monitoring
Namespace: monitoring
Chart: kube-prometheus-stack
```

설치 상태 확인:

```bash
helm list -n monitoring
kubectl get pods -n monitoring
```

## 설치

Prometheus Community Helm Repository를 추가한다.

```bash
helm repo add \
  prometheus-community \
  https://prometheus-community.github.io/helm-charts
```

Repository 정보를 갱신한다.

```bash
helm repo update
```

Monitoring Namespace를 생성한다.

```bash
kubectl create namespace monitoring
```

`kube-prometheus-stack`을 설치한다.

```bash
helm install \
  monitoring \
  prometheus-community/kube-prometheus-stack \
  --version 87.19.1 \
  -n monitoring
```

실습 당시 사용한 Chart 버전을 고정하여 같은 구성을 재현한다. 새 버전으로 올릴 때는 Kubernetes와 Chart의 호환성 및 변경 사항을 먼저 확인한다.

설치된 Pod를 확인한다.

```bash
kubectl get pods -n monitoring
```

다음 Component가 모두 `Running` 상태인지 확인한다.

```text
monitoring-grafana
monitoring-kube-prometheus-operator
monitoring-kube-state-metrics
monitoring-prometheus-node-exporter
prometheus-monitoring-kube-prometheus-prometheus
alertmanager-monitoring-kube-prometheus-alertmanager
```

Helm 설치 완료와 실제 Pod 준비 완료 시점은 다를 수 있다. 모든 Pod가 준비될 때까지 기다린다.

## Grafana 접속

Grafana Service를 Local Port로 전달한다.

```bash
kubectl port-forward \
  service/monitoring-grafana \
  3000:80 \
  -n monitoring
```

Browser에서 접속한다.

```text
http://localhost:3000
```

Port Forward는 명령을 실행한 Terminal Process가 살아 있는 동안만 유지된다.

Mini PC의 Grafana에 다른 PC에서 접속하려면 Network 구성에 따라 SSH Tunnel, Tailscale IP 또는 Listen Address 설정이 필요할 수 있다.

## Grafana 관리자 계정

기본 관리자 ID:

```text
admin
```

관리자 Password 확인:

```bash
kubectl get secret \
  monitoring-grafana \
  -n monitoring \
  -o jsonpath='{.data.admin-password}' \
  | base64 --decode

echo
```

Password는 Terminal이나 문서에 평문으로 저장하지 않는다.

## Prometheus 접속

Prometheus Service를 Local Port로 전달한다.

```bash
kubectl port-forward \
  service/monitoring-kube-prometheus-prometheus \
  9090:9090 \
  -n monitoring
```

Browser:

```text
http://localhost:9090
```

Prometheus API로 Query할 수도 있다.

```bash
curl -sG \
  --data-urlencode 'query=up' \
  http://localhost:9090/api/v1/query
```

## Grafana 기본 화면

### Dashboards

저장된 Dashboard를 확인한다.

`kube-prometheus-stack`은 Kubernetes 상태를 확인할 수 있는 기본 Dashboard를 제공한다.

```text
Kubernetes / Compute Resources / Namespace (Pods)
```

이 Dashboard에서는 Namespace별 CPU, Memory, Network, Storage I/O를 확인할 수 있다.

### Explore

PromQL을 직접 실행하고 결과를 확인하는 화면이다.

예:

```promql
sum(chat_websocket_connections)
```

```promql
count(container_cpu_usage_seconds_total{
  namespace="chat",
  container!=""
})
```

Dashboard Panel을 만들기 전에 Metric과 Query가 정상인지 확인할 때 유용하다.

### Alerting

Metric 조건에 따라 Alert Rule과 Notification을 구성한다.

### Connections

Prometheus 같은 Data Source 연결을 확인하거나 추가한다.

## Chat Application Metric 수집

채팅 서버의 `/metrics` Endpoint:

```bash
curl http://localhost:8080/metrics
```

예:

```text
# HELP chat_websocket_connections Current number of active WebSocket connections.
# TYPE chat_websocket_connections gauge
chat_websocket_connections 0
```

Prometheus Operator 환경에서는 `ServiceMonitor`가 Service를 선택하여 `/metrics`를 수집한다.

```text
chat-app Service
Label: app=chat-app
        ↓
chat-app ServiceMonitor
Path: /metrics
Port: http
        ↓
Prometheus
```

ServiceMonitor 확인:

```bash
kubectl get servicemonitor -n chat
```

Prometheus에서 Metric 확인:

```bash
curl -sG \
  --data-urlencode 'query=chat_websocket_connections' \
  http://localhost:9090/api/v1/query
```

## Dashboard를 볼 때 주의할 점

### `0`과 `No data`는 다르다

```text
0
→ Metric은 존재하지만 현재 값이 0

No data
→ Query 결과가 없거나 Metric 수집에 문제가 있음
```

WebSocket 연결 수가 `0`이면 접속자가 없는 정상 상태일 수 있다.

### 그래프 시작 시점

Prometheus가 Metric을 수집하기 시작한 시점 이전의 데이터는 표시되지 않는다.

Runtime 변경이나 Pod 재생성 직후 그래프가 오른쪽 최근 구간부터 시작하는 것은 정상일 수 있다.

### Kubernetes Metric과 사용자 수는 다르다

CPU, Memory, Network Traffic만으로 접속자 수를 정확하게 계산할 수 없다.

사용자와 관련된 값은 애플리케이션이 직접 Metric으로 제공해야 한다.

## 현재 Monitoring 구성으로 알 수 있는 것

- Namespace와 Pod별 CPU 사용량
- CPU Request와 Limit 대비 사용률
- Pod별 Memory 사용량
- Memory Request와 Limit 대비 사용률
- Network 송수신량과 Packet 수
- Packet Drop
- Storage IOPS와 Throughput
- Pod 상태와 재시작
- 활성 WebSocket 연결 수

아직 별도 Metric을 추가해야 하는 항목:

- 초당 채팅 메시지 수
- 메시지 처리 실패 수
- HTTP 요청 수와 응답 시간
- WebSocket 연결 실패 수
- 고유 사용자 수
- Redis Pub/Sub 처리량
- Database Query 지연시간

---

## 정리

Grafana는 Monitoring Data를 직접 수집하는 도구가 아니라 Prometheus 등의 Data Source를 Query하여 시각화하는 도구다.

현재 프로젝트에서는 Kubernetes 기본 Dashboard로 Infrastructure 상태를 확인하고, Explore 또는 Application Dashboard에서 채팅 서버가 직접 제공하는 Metric을 확인할 수 있다.

```text
Infrastructure Metric
→ 서버가 안정적으로 실행되는가

Application Metric
→ 채팅 기능이 정상적으로 동작하는가
```

두 종류를 함께 관찰해야 서비스 상태를 정확하게 판단할 수 있다.

## Dashboard

이번에 확인한 Dashboard:

```text
Kubernetes / Compute Resources / Namespace (Pods)
```

Data Source:

```text
Prometheus
```

Namespace:

```text
chat
```

`chat` Namespace에는 다음 Workload가 있으므로 Dashboard에 함께 표시된다.

```text
chat-app Pod 3개
postgres Pod 1개
redis Pod 1개
```

이 Dashboard는 Infrastructure 자원 상태를 보여준다. WebSocket 연결 수나 사용자 수 같은 Application Metric은 기본 화면에 포함되지 않는다.

## CPU Dashboard

![[Grafana Namespace Pods CPU 대시보드.png]]

### CPU Utilisation from requests

실제 CPU 사용량이 CPU Request의 몇 %인지 나타낸다.

```text
CPU Request
→ Kubernetes Scheduler가 Pod를 배치할 때 확보해야 한다고 판단하는 CPU
```

예:

```text
CPU Request: 0.1 Core
CPU Usage:   0.01 Core
Utilisation: 10%
```

해석:

- 낮은 값이 지속되면 CPU Request가 실제 사용량보다 클 수 있다.
- 100%를 자주 넘으면 Request가 실제 사용량보다 작을 수 있다.
- HPA가 CPU Request 대비 사용률을 기준으로 동작할 수 있다.

### CPU Utilisation from limits

실제 CPU 사용량이 CPU Limit의 몇 %인지 나타낸다.

```text
CPU Limit
→ Container가 사용할 수 있는 CPU 최대값
```

100%에 가까운 상태가 지속되면 CPU Throttling이 발생할 수 있다.

### CPU Usage

Pod별 실제 CPU Core 사용량의 시간 변화를 보여준다.

```text
1.0  = CPU 1 Core
0.1  = CPU 0.1 Core
0.01 = CPU 0.01 Core
```

확인할 수 있는 내용:

- 어느 Pod가 CPU를 가장 많이 사용하는가
- 특정 시점에 CPU가 급증했는가
- 부하 테스트 중 CPU가 어떻게 변하는가
- Chat Application, PostgreSQL, Redis 중 병목이 어디인가

### CPU Quota

Pod별 CPU 설정과 실제 사용량을 표로 비교한다.

| 항목 | 의미 |
|---|---|
| CPU Usage | 현재 실제 CPU 사용량 |
| CPU Requests | 예약한 CPU |
| CPU Requests % | Request 대비 사용률 |
| CPU Limits | 최대 CPU |
| CPU Limits % | Limit 대비 사용률 |

현재 Chat Pod 설정 예:

```text
CPU Request: 100m = 0.1 Core
CPU Limit:   1 Core
```

## Memory와 현재 Network 사용량

![[Grafana Namespace Pods 메모리와 네트워크 표.png]]

### Memory Usage without cache

File Cache를 제외한 Pod별 주요 Memory 사용량을 보여준다.

단위:

```text
MiB = 1024 × 1024 Bytes
```

확인할 수 있는 내용:

- 어느 Pod가 Memory를 많이 사용하는가
- WebSocket 연결 증가와 함께 Memory가 증가하는가
- 시간이 지나도 Memory가 계속 상승하는가
- PostgreSQL이나 Redis의 Memory 사용량이 급증하는가

Memory가 장시간 계속 증가하고 감소하지 않으면 다음 문제를 의심할 수 있다.

- Memory Leak
- 종료되지 않은 Goroutine
- 정리되지 않은 WebSocket Connection
- Message Buffer 증가
- Cache 증가

### Memory Quota

| 항목 | 의미 |
|---|---|
| Memory Usage | Cache를 제외한 주요 사용량 |
| Memory Requests | 예약한 Memory |
| Memory Requests % | Request 대비 사용률 |
| Memory Limits | 최대 Memory |
| Memory Limits % | Limit 대비 사용률 |
| Memory Usage RSS | 실제 RAM에 상주하는 Memory |
| Memory Usage Cache | File System Cache |

현재 Chat Pod 설정 예:

```text
Memory Request: 64 MiB
Memory Limit:   256 MiB
```

Memory Limit에 가까워지면 Container가 `OOMKilled`될 수 있다.

Pod 종료 원인 확인:

```bash
kubectl describe pod \
  <POD_NAME> \
  -n chat
```

### Current Network Usage

Pod별 현재 Network 상태를 표로 보여준다.

| 항목 | 의미 |
|---|---|
| Current Receive Bandwidth | 초당 수신 Byte |
| Current Transmit Bandwidth | 초당 전송 Byte |
| Rate of Received Packets | 초당 수신 Packet |
| Rate of Transmitted Packets | 초당 전송 Packet |
| Received Packets Dropped | 초당 손실된 수신 Packet |
| Transmitted Packets Dropped | 초당 손실된 전송 Packet |

Chat Pod의 Network Traffic에는 다음 통신이 모두 포함될 수 있다.

- WebSocket 연결과 Message
- Health Check
- Redis Pub/Sub 통신
- PostgreSQL 접근
- Kubernetes 내부 통신

따라서 Network Traffic만으로 접속자 수나 Message 수를 정확하게 계산할 수 없다.

## Network Graph

![[Grafana Namespace Pods 네트워크 그래프.png]]

### Receive Bandwidth

Pod가 초당 수신한 Data 크기다.

단위 예:

```text
b/s
kb/s
MB/s
```

WebSocket Client가 Message를 전송하거나 내부 Component가 요청을 보내면 값이 증가할 수 있다.

### Transmit Bandwidth

Pod가 초당 전송한 Data 크기다.

Chat Server가 Client에게 Message를 Broadcast하면 Chat Pod의 Transmit Bandwidth가 증가할 수 있다.

### Rate of Received Packets

Pod가 초당 받은 Network Packet 수다.

### Rate of Transmitted Packets

Pod가 초당 보낸 Network Packet 수다.

Packet 하나가 Chat Message 하나를 의미하지는 않는다. 하나의 Message가 여러 Packet으로 나뉠 수 있고 Protocol 제어 Packet도 포함된다.

### Received Packets Dropped

수신 과정에서 처리되지 못하고 버려진 Packet 수다.

### Transmitted Packets Dropped

전송 과정에서 처리되지 못하고 버려진 Packet 수다.

정상 상태에서는 일반적으로 `0 p/s`다.

지속적으로 증가하면 다음을 점검한다.

- Node Network 혼잡
- CNI 문제
- Network Buffer 부족
- CPU 과부하
- Interface Error

## Packet Drop과 Storage I/O

![[Grafana Namespace Pods 패킷과 스토리지 IO.png]]

### IOPS Reads + Writes

초당 Storage 읽기와 쓰기 작업 횟수다.

```text
IOPS = Input/Output Operations Per Second
```

예:

```text
1 io/s
→ 1초에 평균 1번의 읽기 또는 쓰기 작업
```

PostgreSQL에서 데이터 저장이나 조회가 증가하면 IOPS가 증가할 수 있다.

### Throughput Read + Write

Storage에서 초당 읽거나 쓴 Data 크기다.

```text
IOPS
→ 작업 횟수

Throughput
→ 전송한 Data 크기
```

작은 Data를 자주 읽고 쓰면 IOPS는 높고 Throughput은 낮을 수 있다.

큰 Data를 적은 횟수로 읽고 쓰면 IOPS는 낮고 Throughput은 높을 수 있다.

### Current Storage IO

Pod별 읽기와 쓰기를 표로 비교한다.

| 항목 | 의미 |
|---|---|
| IOPS Reads | 초당 읽기 작업 |
| IOPS Writes | 초당 쓰기 작업 |
| IOPS Reads + Writes | 전체 작업 횟수 |
| Throughput Read | 초당 읽은 Data |
| Throughput Write | 초당 쓴 Data |
| Throughput Read + Write | 전체 Data 전송량 |

Chat Application보다 PostgreSQL의 Disk I/O 변화가 더 크게 나타날 수 있다.

## Request와 Limit 해석

### Request

Kubernetes가 Pod를 Node에 배치할 때 기준으로 사용하는 최소 예약 자원이다.

```yaml
resources:
  requests:
    cpu: 100m
    memory: 64Mi
```

Request를 너무 크게 설정하면 실제 자원이 남아 있어도 새로운 Pod를 배치하기 어려울 수 있다.

Request를 너무 작게 설정하면 Node에 너무 많은 Pod가 배치될 수 있다.

### Limit

Container가 사용할 수 있는 최대 자원이다.

```yaml
resources:
  limits:
    cpu: "1"
    memory: 256Mi
```

CPU Limit을 넘으려고 하면 CPU Throttling이 발생할 수 있다.

Memory Limit을 넘으면 OOM으로 Container가 종료될 수 있다.

- Chat Pod 3개가 Metric을 정상 제공하는가

- Packet Drop이 발생하는가

## 현재 Dashboard로 알 수 없는 것

이 Dashboard만으로 다음 내용은 알 수 없다.

- 현재 접속한 사용자 수
- 활성 WebSocket 연결 수
- 고유 사용자 수
- 초당 Chat Message 수
- Message 처리 성공·실패 수
- HTTP 응답 시간
- WebSocket 연결 실패 수
- Database Query 지연시간
- Redis Pub/Sub 처리량

이 값들은 Application이 직접 Metric으로 제공해야 한다.

현재 구현된 Application Metric:

```text
chat_websocket_connections
```

전체 활성 WebSocket 연결 수:

```promql
sum(chat_websocket_connections)
```

이 값은 고유 사용자 수가 아니라 연결 수다.

## Dashboard 확인 순서

장애나 부하를 분석할 때 다음 순서로 확인한다.

### 1. Pod가 실행 중인지 확인

```bash
kubectl get pods -n chat
```

### 2. CPU와 Memory 확인

- CPU Request와 Limit 대비 사용률
- Memory Limit 접근 여부
- 특정 Pod만 비정상적으로 높은지

### 3. Network 확인

- 송수신량 급증
- Packet Rate 증가
- Packet Drop 발생

### 4. Storage 확인

- PostgreSQL IOPS 증가
- Throughput 급증
- 지속적인 Disk I/O 병목

### 5. Application Metric 확인

- WebSocket 연결 수
- 이후 추가할 Message 처리량
- Error 수와 응답 시간

Infrastructure Metric과 Application Metric을 같은 시간 범위로 비교해야 원인을 정확히 찾을 수 있다.

## 그래프가 최근 구간부터 시작한 이유

이번 환경에서는 Minikube Runtime을 Docker에서 containerd로 변경한 뒤 Container Label이 정상적으로 수집되기 시작하였다.

```text
변경 전
container=""
image=""
name=""

변경 후
container="chat-app"
image="ghcr.io/pang-4/chat-app:..."
name="<CONTAINER_ID>"
```

Prometheus에는 Runtime 변경 이후부터 정상 Label의 새 Time Series가 생성되었다.

따라서 `Last 1 hour`를 선택해도 변경 이전 구간은 비어 있고 최근 구간부터 그래프가 나타나는 것이 정상이다.

시간이 지나면 그래프가 계속 채워진다.

관련 Troubleshooting:

```text
00_트러블슈팅/
Grafana Kubernetes 대시보드에 Pod 메트릭이 표시되지 않는 문제
```

## 정리

Kubernetes 기본 Pod Dashboard는 Infrastructure 상태를 확인하는 화면이다.

```text
CPU·Memory
→ 자원 부족과 병목

Network
→ Traffic과 Packet 손실

Storage I/O
→ Disk 작업량과 처리량

Request·Limit
→ Kubernetes 자원 설정의 적절성
```

이 Dashboard를 통해 서버가 안정적으로 실행되는지는 판단할 수 있지만 사용자가 어떤 기능을 얼마나 사용하는지는 알 수 없다.

Application 상태까지 확인하려면 WebSocket 연결 수, Message 처리량, Error, Latency 같은 별도의 Application Metric을 함께 구성해야 한다.

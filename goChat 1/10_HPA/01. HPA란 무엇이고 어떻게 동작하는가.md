## HPA란

HPA는 `Horizontal Pod Autoscaler`의 약자다.

애플리케이션의 부하가 증가하거나 감소할 때 Kubernetes가 Pod 개수를 자동으로 조절하는 기능이다.

```text
사용자 요청 증가
        ↓
Pod CPU 사용률 증가
        ↓
HPA가 Metric 확인
        ↓
Deployment의 replicas 증가
        ↓
새로운 Pod 생성
```

부하가 줄어들면 반대 방향으로 동작한다.

```text
사용자 요청 감소
        ↓
Pod CPU 사용률 감소
        ↓
안정화 시간 동안 관찰
        ↓
Deployment의 replicas 감소
        ↓
불필요한 Pod 종료
```

Horizontal은 Pod의 크기를 키우는 것이 아니라 같은 Pod를 옆으로 더 추가한다는 의미다.

---

## Horizontal Scaling과 Vertical Scaling

| 구분 | 의미 | 예시 |
|---|---|---|
| Horizontal Scaling | Pod 또는 서버 개수를 늘림 | Pod 3개 → 6개 |
| Vertical Scaling | 한 Pod에 할당하는 CPU와 Memory를 늘림 | CPU 200m → 500m |

HPA는 Horizontal Scaling을 담당한다.

Pod의 CPU·Memory 요청량을 자동으로 변경하는 기능은 VPA(Vertical Pod Autoscaler)다.

---

## 현재 채팅 프로젝트의 HPA 구성

현재 설정 파일:

```text
k8s/chat-hpa.yaml
```

핵심 설정:

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: chat-app
  namespace: chat
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: chat-app
  minReplicas: 3
  maxReplicas: 6
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70
```

각 항목의 의미:

| 항목 | 현재 값 | 의미 |
|---|---:|---|
| `scaleTargetRef` | `Deployment/chat-app` | HPA가 Pod 개수를 조절할 대상 |
| `minReplicas` | 3 | 부하가 없어도 유지할 최소 Pod 수 |
| `maxReplicas` | 6 | HPA가 확장할 수 있는 최대 Pod 수 |
| `resource.name` | `cpu` | 확장 판단에 사용할 Metric |
| `averageUtilization` | 70 | CPU Request 대비 평균 사용률 목표 |

즉, Chat Pod들의 평균 CPU 사용률이 CPU Request의 70%를 넘으면 HPA가 Pod 추가를 검토한다.

---

## CPU 70%의 정확한 의미

HPA의 CPU 사용률은 장비 전체 CPU의 70%가 아니다.

Deployment에 설정된 각 Container의 `resources.requests.cpu`를 기준으로 계산한다.

예를 들어 Chat Container의 CPU Request가 `100m`일 때 실제 사용량이 `70m`이면 HPA 관점의 CPU 사용률은 70%다.

```text
CPU 사용률 = 실제 CPU 사용량 ÷ CPU Request × 100
           = 70m ÷ 100m × 100
           = 70%
```

따라서 CPU 기반 HPA를 사용하려면 대상 Container에 `resources.requests.cpu`가 설정되어 있어야 한다.

확인:

```bash
kubectl get deployment chat-app -n chat \
  -o jsonpath='{.spec.template.spec.containers[*].resources}'
```

---

## HPA의 Pod 수 계산 원리

HPA는 대략 다음 비율로 필요한 Pod 수를 계산한다.

```text
원하는 Pod 수
= 올림(현재 Pod 수 × 현재 CPU 사용률 ÷ 목표 CPU 사용률)
```

예를 들어 현재 Pod가 3개이고 평균 CPU 사용률이 140%, 목표가 70%라면:

```text
올림(3 × 140 ÷ 70)
= 올림(6)
= 6개
```

하지만 실제 변경 속도는 `behavior` 정책, 최소·최대 Pod 수, Metric 수집 주기와 Pod 준비 시간의 영향을 받는다.

---

## Scale Up 정책

현재 설정:

```yaml
behavior:
  scaleUp:
    stabilizationWindowSeconds: 0
    selectPolicy: Max
    policies:
      - type: Pods
        value: 2
        periodSeconds: 60
      - type: Percent
        value: 100
        periodSeconds: 60
```

의미:

- 확장이 필요하면 별도의 안정화 대기 없이 반응한다.
- 60초 동안 최대 2개 Pod를 추가할 수 있다.
- 또는 기존 Pod 수의 최대 100%만큼 늘릴 수 있다.
- `selectPolicy: Max`이므로 두 정책 중 더 많이 확장할 수 있는 정책을 선택한다.
- 단, 전체 Pod 수는 `maxReplicas: 6`을 넘을 수 없다.

이번 300명 테스트에서는 다음 흐름이 관찰되었다.

```text
CPU 3% → 28% → 83% → 157% → 209%
Pod 3개 → 4개 → 6개
```

이는 CPU 사용률이 목표 70%를 넘자 HPA가 정상적으로 확장한 결과다.

---

## Scale Down 정책

현재 설정:

```yaml
behavior:
  scaleDown:
    stabilizationWindowSeconds: 300
    selectPolicy: Max
    policies:
      - type: Percent
        value: 25
        periodSeconds: 60
```

의미:

- CPU가 내려가도 바로 Pod를 제거하지 않는다.
- 최근 5분 동안의 권장 Pod 수를 관찰한다.
- 축소할 때는 60초마다 현재 Pod 수의 최대 25%만 줄인다.
- 최소 3개 아래로는 줄이지 않는다.

축소를 천천히 하는 이유는 부하가 잠시 내려갔다가 다시 상승할 때 Pod가 반복해서 생성·삭제되는 현상을 줄이기 위해서다.

정상적인 축소 흐름:

```text
부하 테스트 종료
        ↓
CPU 사용률 감소
        ↓
5분 안정화 대기
        ↓
Pod 6개 → 4개 → 3개
```

HPA에 `ScaleDownStabilized`가 표시되는 것은 오류가 아니라 안정화 시간 동안 기다리고 있다는 의미다.

## HPA 동작에 필요한 구성요소

```text
각 Pod의 CPU 사용량
        ↓
Metrics Server
        ↓
Kubernetes Metrics API
        ↓
HPA Controller
        ↓
Deployment replicas 변경
        ↓
새 Pod 생성 또는 기존 Pod 종료
```

### Metrics Server

HPA가 CPU와 Memory 사용량을 조회할 수 있도록 Kubernetes Metrics API를 제공한다.

확인:

```bash
kubectl top pods -n chat
```

이 명령이 정상적으로 값을 보여줘야 CPU 기반 HPA도 Metric을 계산할 수 있다.

### Deployment

HPA는 Pod를 직접 생성하지 않는다.

`Deployment/chat-app`의 원하는 복제본 수를 변경하고, Deployment와 ReplicaSet이 실제 Pod를 생성하거나 종료한다.

### CPU Request

HPA가 CPU 사용률을 계산하는 기준값이다.

CPU Request가 없으면 CPU 사용률을 정상적으로 계산하지 못할 수 있다.

## 상태 확인 명령

### 현재 HPA 상태

```bash
kubectl get hpa -n chat
```

예시:

```text
NAME       REFERENCE             TARGETS        MINPODS   MAXPODS   REPLICAS
chat-app   Deployment/chat-app   cpu: 83%/70%   3         6         4
```

| 출력 | 의미 |
|---|---|
| `cpu: 83%/70%` | 현재 평균 CPU 사용률 83%, 목표 70% |
| `MINPODS` | 최소 Pod 수 |
| `MAXPODS` | 최대 Pod 수 |
| `REPLICAS` | 현재 HPA가 관리하는 Pod 수 |

### 실시간 관찰

```bash
kubectl get hpa -n chat -w
```

다른 Terminal:

```bash
kubectl get pods -n chat -w
```

### 상세 원인과 Event 확인

```bash
kubectl describe hpa chat-app -n chat
```

중요한 Condition:

| Condition 또는 Reason | 의미 |
|---|---|
| `AbleToScale=True` | 대상 Deployment의 크기를 변경할 수 있음 |
| `ScalingActive=True` | Metric을 정상적으로 읽고 계산 중 |
| `ValidMetricFound` | 유효한 CPU Metric 확인 |
| `ScaleDownStabilized` | 축소 안정화 시간 때문에 대기 중 |
| `ScalingLimited=True` | 최소 또는 최대 Pod 수 제한에 도달 |


```text
0 → 300까지 증가

```

### Pod별 WebSocket 연결 수


이 Query는 합계가 아니라 Pod마다 별도의 선을 보여준다.

기존 WebSocket 연결은 HPA로 새 Pod가 생성되더라도 새 Pod로 이동하지 않는다. 새 Pod가 준비된 후 들어오는 신규 연결부터 Service 또는 Ingress가 분산한다.

## 이 프로젝트의 HPA 부하 테스트

### 테스트 목적

- 300개의 WebSocket 연결을 처리할 수 있는지 확인
- 각 사용자가 주기적으로 메시지를 보낼 수 있는지 확인
- 메시지가 WebSocket으로 다시 전달되는지 확인
- CPU 증가에 따라 Chat Pod가 자동 확장되는지 확인
- 부하 종료 후 Pod가 최소 개수로 자동 축소되는지 확인

### 테스트 경로

```text
Mac의 k6
  ↓ Tailscale
Mini PC의 socat
  ↓
Minikube Ingress NodePort
  ↓
Chat Service
  ↓
Chat Pod 3~6개
  ↓
Redis Broadcast와 PostgreSQL
```

Mini PC에서 사용하는 TCP 중계:

```bash
socat \
  TCP-LISTEN:8080,bind=100.126.215.15,reuseaddr,fork \
  TCP:192.168.49.2:31673
```

`socat`은 Mac에서 접근 가능한 Mini PC의 Tailscale 주소와 Minikube 내부 NodePort를 연결한다.

### `kubectl port-forward`를 사용하지 않는 이유

`kubectl port-forward`는 개발과 간단한 점검에 적합한 임시 통로다.

300명 테스트에서는 많은 WebSocket Broadcast Traffic이 하나의 Port Forward 경로로 전달되면서 다음 오류가 발생했다.

```text
write: broken pipe
error: lost connection to pod
```

이때 Chat Pod와 HPA는 동작했지만 외부 연결 통로가 끊겨 메시지 전달 검증이 실패했다.

따라서 최종 부하 테스트에서는 `socat`을 통해 Ingress NodePort로 전달하는 경로를 사용한다.

운영 환경에서는 `socat` 대신 다음과 같은 정식 외부 진입점을 사용한다.

- Cloud LoadBalancer
- MetalLB
- 외부 IP가 있는 Ingress Controller
- DNS와 TLS가 설정된 Load Balancer

## 자주 발생하는 문제

### `cpu: <unknown>/70%`

가능한 원인:

- Metrics Server가 설치되지 않았거나 비정상
- 대상 Container에 CPU Request가 없음
- 새 Pod의 Metric이 아직 수집되지 않음

확인:

```bash
kubectl top pods -n chat
kubectl describe hpa chat-app -n chat
```

### CPU가 낮은데 Pod가 바로 줄지 않음

`scaleDown.stabilizationWindowSeconds: 300` 설정 때문에 5분 동안 기다리는 정상 동작일 수 있다.

```bash
kubectl describe hpa chat-app -n chat
```

`ScaleDownStabilized`가 표시되는지 확인한다.

### CPU가 높은데 6개보다 증가하지 않음

현재 `maxReplicas: 6`이므로 정상이다.

`ScalingLimited=True` 또는 최대 Replica 제한 관련 Message가 표시될 수 있다.

### HPA가 확장됐는데 기존 연결이 새 Pod로 이동하지 않음

WebSocket은 연결이 만들어진 시점의 Pod와 장시간 유지되는 연결이다.

HPA가 새 Pod를 추가해도 기존 연결을 강제로 재분배하지 않는다. 새롭게 연결되는 사용자부터 새 Pod로 분산된다.

이 때문에 WebSocket 서비스는 연결 수, 메시지 처리량, CPU 사용량과 신규 연결 분산을 함께 관찰해야 한다.

## 핵심 정리

```text
HPA는 Metric을 기준으로 Deployment의 Pod 개수를 자동 조절한다.
현재 프로젝트는 CPU Request 대비 평균 70%를 목표로 사용한다.
Chat Pod는 최소 3개, 최대 6개로 동작한다.
확장은 빠르게, 축소는 5분 안정화 후 천천히 진행한다.
WebSocket의 기존 연결은 새 Pod로 자동 이동하지 않는다.
Metrics Server는 HPA에 현재 Metric을 제공한다.
Prometheus와 Grafana는 HPA와 애플리케이션 상태를 관찰하고 분석한다.
```

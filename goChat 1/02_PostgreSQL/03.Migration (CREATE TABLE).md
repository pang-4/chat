# Migration: `messages` 테이블 생성

## 목표

Go 서버가 시작될 때 PostgreSQL에 `messages` 테이블이 없으면 자동으로 생성한다.

현재 단계에서는 별도의 Migration Tool을 사용하지 않고, Go 코드에서 `CREATE TABLE IF NOT EXISTS`를 실행하여 애플리케이션에 필요한 초기 테이블을 준비한다.

---

## 전체 실행 흐름

```text
Go 서버 실행
↓
환경변수 로드
↓
PostgreSQL 연결
↓
PingContext로 연결 확인
↓
Migrate(ctx, db)
↓
CREATE TABLE IF NOT EXISTS messages
↓
테이블 준비 완료
↓
Hub와 HTTP 서버 실행
```

Migration은 PostgreSQL 연결에 성공한 뒤, WebSocket 서버를 실행하기 전에 수행한다.

테이블 생성에 실패하면 서버를 실행하지 않는다. 메시지를 저장할 수 없는 상태에서 채팅 요청을 받지 않기 위해서다.

---

## 프로젝트 파일

```text
app/
└── internal/
    └── database/
        ├── database.go            # PostgreSQL 연결
        ├── migrate.go             # messages 테이블 준비
        └── message_repository.go  # 채팅 메시지 저장
```

각 파일의 역할을 분리하였다.

- `database.go`: DB 연결과 Connection Pool 설정
- `migrate.go`: 애플리케이션에 필요한 테이블 준비
- `message_repository.go`: 준비된 테이블에 메시지 저장

---

## 현재 `migrate.go`

```go
package database

import (
    "context"
    "database/sql"
    "fmt"
)

func Migrate(ctx context.Context, db *sql.DB) error {
    query := `
    CREATE TABLE IF NOT EXISTS messages (
        id SERIAL PRIMARY KEY,
        sender TEXT NOT NULL,
        content TEXT NOT NULL,
        created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
    );
    `

    _, err := db.ExecContext(ctx, query)
    if err != nil {
        return fmt.Errorf("create messages table: %w", err)
    }

    return nil
}
```

---

## `Migrate()` 함수

```go
func Migrate(ctx context.Context, db *sql.DB) error
```

### `ctx context.Context`

Migration 작업의 취소 신호를 전달한다.

서버 종료 요청이 발생하거나 상위 Context가 취소되면 PostgreSQL 작업도 취소할 수 있다.

### `db *sql.DB`

`database.Open()`에서 생성하고 연결을 확인한 DB Connection Pool이다.

새로운 DB 연결을 다시 만들지 않고, 애플리케이션 전체가 사용하는 같은 `sql.DB`를 전달받는다.

### `error`

테이블 생성에 성공하면 `nil`, 실패하면 오류를 반환한다.

호출한 쪽에서 오류를 확인하여 서버 실행 여부를 결정할 수 있다.

## `CREATE TABLE IF NOT EXISTS`

```sql
CREATE TABLE IF NOT EXISTS messages (
    id SERIAL PRIMARY KEY,
    sender TEXT NOT NULL,
    content TEXT NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

### 첫 실행

```text
messages 테이블 없음
↓
새로운 테이블 생성
```

### 두 번째 이후 실행

```text
messages 테이블 있음
↓
새로 생성하지 않고 그대로 사용
```

따라서 서버를 여러 번 실행해도 테이블이 이미 존재한다는 오류가 발생하지 않는다.

---

## 각 Column의 역할

| Column | Type | 제약조건 | 역할 |
|---|---|---|---|
| `id` | `SERIAL` | `PRIMARY KEY` | 메시지를 구분하는 자동 증가 번호 |
| `sender` | `TEXT` | `NOT NULL` | 메시지를 보낸 사용자 이름 |
| `content` | `TEXT` | `NOT NULL` | 채팅 내용 |
| `created_at` | `TIMESTAMP` | `DEFAULT CURRENT_TIMESTAMP` | 메시지가 저장된 시각 |

### `id SERIAL PRIMARY KEY`

```sql
id SERIAL PRIMARY KEY
```

`SERIAL`은 새로운 Row가 저장될 때 증가하는 번호를 만든다.

`PRIMARY KEY`이므로 각 메시지의 ID는 고유하며 `NULL`이 될 수 없다.

```text
1
2
3
...
```

### `sender TEXT NOT NULL`

```sql
sender TEXT NOT NULL
```

메시지를 보낸 사용자의 이름을 저장한다.

`NOT NULL`이므로 값 없이 저장할 수 없다. Handler에서 검증한 `Client.Name`이 저장된다.

### `content TEXT NOT NULL`

```sql
content TEXT NOT NULL
```

채팅 내용을 저장한다.

`NOT NULL`은 `NULL`을 막지만 빈 문자열까지 자동으로 막지는 않는다. 빈 문자열과 최대 길이는 Handler에서 검증한다.

### `created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP`

```sql
created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
```

메시지가 DB에 저장된 시각을 PostgreSQL이 자동으로 기록한다.

Go에서 `created_at` 값을 INSERT하지 않아도 기본값인 `CURRENT_TIMESTAMP`가 사용된다.

---

## 왜 `ExecContext()`를 사용하는가?

```go
_, err := db.ExecContext(ctx, query)
```

`CREATE TABLE`은 조회할 Row를 반환하지 않으므로 `ExecContext()`를 사용한다.

주로 다음 SQL에 사용한다.

- `CREATE TABLE`
- `ALTER TABLE`
- `INSERT`에서 반환값이 필요하지 않은 경우
- `UPDATE`
- `DELETE`

`Exec()` 대신 `ExecContext()`를 사용하면 상위 Context의 취소 신호를 DB 작업에 전달할 수 있다.

데이터를 조회하거나 반환받아야 할 때는 목적에 따라 다음 함수를 사용한다.

- 여러 Row 조회: `QueryContext()`
- 한 Row 조회: `QueryRowContext()`

현재 메시지 저장에서는 생성된 `id`와 `created_at`을 받아야 하므로 `QueryRowContext()`를 사용한다.

---

## 오류를 감싸서 반환하는 이유

```go
return fmt.Errorf("create messages table: %w", err)
```

PostgreSQL이 반환한 원래 오류에 어떤 작업이 실패했는지 설명을 추가한다.

예를 들어 권한 문제로 SQL 실행에 실패하면 단순한 DB 오류가 아니라 `messages` 테이블 생성 중 실패했다는 사실까지 알 수 있다.

`%w`를 사용했기 때문에 원래 오류 정보도 유지된다.

## `application.Run()`에서 호출

```go
db, err := database.Open(ctx, cfg.Database)
if err != nil {
    return err
}
defer db.Close()

if err := database.Migrate(ctx, db); err != nil {
    return err
}
```

실행 순서가 중요하다.

```text
DB 연결 성공
↓
Migration 성공
↓
Repository 생성
↓
WebSocket 서버 실행
```

Migration을 실행하지 않고 메시지를 저장하면 다음 오류가 발생할 수 있다.

```text
relation "messages" does not exist
```

## 메시지 저장과 연결되는 과정

Migration으로 테이블을 준비한 뒤 `message_repository.go`에서 메시지를 저장한다.

```sql
INSERT INTO messages (sender, content)
VALUES ($1, $2)
RETURNING id, created_at;
```

```text
Migration
↓
messages 테이블 준비
↓
WebSocket 채팅 수신
↓
MessageRepository.Save()
↓
메시지 INSERT
↓
id와 created_at 반환
↓
저장된 메시지 Broadcast
```

## 현재 방식의 중요한 한계

`CREATE TABLE IF NOT EXISTS`는 테이블이 없을 때만 생성한다.

이미 존재하는 테이블의 구조를 새로운 SQL에 맞게 변경하지는 않는다.

예를 들어 나중에 SQL에 다음 Column을 추가해도

```sql
room_id TEXT
```

기존 `messages` 테이블이 이미 존재하면 자동으로 추가되지 않는다.

```text
CREATE TABLE IF NOT EXISTS
↓
테이블이 이미 존재함
↓
아무 변경도 하지 않음
```

따라서 현재 방식은 정확히 말하면 **초기 Schema 생성 또는 간단한 Migration 단계**에 가깝다.

DB 구조 변경 이력을 순서대로 관리하는 완전한 버전 관리형 Migration은 아니다.

---

## 앞으로 테이블 구조가 변경된다면

프로젝트가 확장되어 Column이나 Table 변경이 많아지면 Migration Tool을 도입할 수 있다.

예를 들면 다음과 같다.

- `golang-migrate`
- Goose
- Flyway
- Liquibase

Migration 파일을 사용하면 다음과 같이 변경 순서를 관리할 수 있다.

```text
001_create_messages.up.sql
002_add_room_id.up.sql
003_add_message_index.up.sql
```

그리고 DB에는 어떤 Migration까지 실행했는지 기록한다.

이 방식의 장점은 다음과 같다.

- DB 변경 이력 관리
- 개발·테스트·운영 환경에 같은 순서로 적용
- 이미 실행한 변경의 중복 실행 방지
- 팀 개발 시 Schema 상태 공유
- 필요한 경우 Rollback 관리

---

## 현재 Migration Tool을 사용하지 않는 이유

현재 프로젝트는 학습 단계이며 아직 테이블이 하나뿐이다.

지금은 Tool 사용법보다 다음 원리를 직접 이해하는 것을 우선한다.

- Go가 SQL을 실행하는 방법
- `Context`를 DB 작업에 전달하는 방법
- PostgreSQL이 테이블을 생성하는 과정
- 서버 시작 순서와 DB 준비 상태의 관계
- SQL 오류를 Go에서 처리하는 방법

테이블 구조 변경이 본격적으로 시작되면 그 시점에 버전 관리형 Migration Tool을 도입하는 것이 적절하다.

- Migration과 초기 Schema 생성의 차이
- `CREATE TABLE IF NOT EXISTS`
- `SERIAL`
- `PRIMARY KEY`
- `NOT NULL`
- `TIMESTAMP`

## 핵심 요약

```text
database.Open()
↓
PostgreSQL 연결 확인
↓
database.Migrate(ctx, db)
↓
messages 테이블이 없으면 생성
↓
Repository와 WebSocket 서버 실행
```

현재 `Migrate()`의 목적은 서버가 메시지를 저장할 수 있도록 최초 실행에 필요한 `messages` 테이블을 준비하는 것이다.

`IF NOT EXISTS`는 반복 실행을 안전하게 만들지만 기존 테이블의 구조 변경까지 처리하지는 않는다. Schema 변경이 많아지는 단계에서는 별도의 Migration Tool과 버전별 SQL 파일이 필요하다.

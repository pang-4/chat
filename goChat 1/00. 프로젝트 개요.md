# Go WebSocket Chat Platform 프로젝트 개요

## 프로젝트 소개

이 프로젝트는 Go로 실시간 WebSocket 채팅 서버를 구현하고, 컨테이너화부터 Kubernetes 운영, GitOps 배포, 모니터링과 부하 테스트까지 하나의 흐름으로 구축한 DevOps 포트폴리오다.

단일 서버에서 채팅 기능만 동작시키는 데서 끝나지 않고 다음 질문에 답하는 것을 목표로 했다.

```text
Chat Pod가 여러 개일 때 모든 사용자가 같은 Message를 받을 수 있는가?
Message를 영구 저장할 수 있는가?
배포를 자동화하고 변경 이력을 추적할 수 있는가?
부하가 증가하면 Pod를 자동으로 늘릴 수 있는가?
성능과 장애를 Metric으로 확인할 수 있는가?
300명의 WebSocket 사용자를 실제로 처리할 수 있는가?
```

## 해결한 핵심 문제

### 여러 Chat Pod의 Broadcast

각 Go Process의 Hub는 자신의 Memory 안에만 존재한다.

```text
Pod 1 Hub ≠ Pod 2 Hub ≠ Pod 3 Hub
```

Redis Pub/Sub을 공용 Event Bus로 사용하여 한 Pod에서 받은 Message를 모든 Pod가 Subscribe하도록 구성했다.

```text
Client → Pod 1 → PostgreSQL → Redis Publish
                                ↓
                    Pod 1, Pod 2, Pod 3 Subscribe
                                ↓
                    각 Pod의 Client에게 Broadcast
```

### Message 영속성과 실시간 전달 순서

Chat Message를 먼저 PostgreSQL에 저장하고 DB가 발급한 ID와 생성 시간을 포함한 Message를 Redis에 Publish한다.

```text
입력 검증
→ PostgreSQL INSERT
→ id, created_at 반환
→ Redis Publish
→ WebSocket Broadcast
```

이를 통해 Client가 수신한 Chat Message가 실제 저장 결과와 연결된다.

### 부하에 따른 자동 확장

Chat Pod의 CPU Request를 기준으로 평균 사용률 70%를 HPA 목표로 설정했다.

```text
minReplicas: 3
maxReplicas: 6
CPU target: 70%
```

300명 테스트에서 CPU가 최대 247%까지 증가했고 Pod가 `3 → 6`으로 확장됐다. 테스트 종료 후 5분 안정화 시간을 거쳐 `6 → 4 → 3`으로 축소됐다.

## 주요 기술 선택

### Go

WebSocket Connection마다 Read와 Write를 독립적으로 처리하고 Channel 기반 Hub로 Client 등록·해제와 Broadcast를 직렬화하기 위해 사용했다.

### PostgreSQL

채팅 Message를 영구 저장하고 ID와 생성 시간을 일관되게 관리한다.

### Redis Pub/Sub

여러 Chat Pod의 Memory Hub 사이에서 실시간 Message를 전달한다. 영구 저장소가 아니라 실행 중 Event 전달 통로다.

### Kubernetes와 Minikube

Deployment, Service, Ingress, Probe, Secret, ConfigMap, StatefulSet, PVC와 HPA를 실제로 구성하고 검증하기 위해 사용했다.

### GitHub Actions와 ArgoCD

CI가 Test와 Image 생성을 담당하고, ArgoCD가 Git의 Kubernetes Manifest를 Cluster에 동기화하도록 역할을 분리했다.

### Prometheus와 Grafana

CPU, Memory, Network, Storage I/O와 Application의 WebSocket Connection Metric을 시간 흐름에 따라 분석했다.

### k6

WebSocket Connection, Message 송수신, DB ID, Message 지연과 정상 종료를 자동 검증했다.

## 300명 최종 검증

```text
Connection 성공률: 100% (300/300)
Message 전달 성공률: 100% (300/300)
Check: 225,290/225,290
정상 완료: 300
중단: 0
Packet Drop: 0
```

성능:

```text
연결 p95: 104.44ms
Message 평균: 207.49ms
Message p95: 823.79ms
Message 최대: 6.4초
수신 Message: 29,361,590개
수신 데이터: 4.0GB
```

Message 전달 자체는 모두 성공했지만 최대 지연이 6.4초까지 증가했다. 더 큰 사용자 수를 목표로 한다면 PostgreSQL Write, Broadcast 방식, Message 빈도와 Room 분리 전략을 추가로 최적화해야 한다.

## 프로젝트 결과

이 프로젝트를 통해 Application 구현부터 Container, Kubernetes, CI/CD, GitOps, Observability와 Load Test까지 연결된 운영 흐름을 직접 구축했다.

특히 기능 구현만이 아니라 실패한 테스트의 Metric과 Log를 근거로 원인을 구분하고, Script와 Network 진입 경로를 수정한 뒤 동일 조건에서 재검증했다.

## ArgoCD란

ArgoCD는 Git 저장소에 기록된 Kubernetes 설정을 기준으로 Cluster의 배포 상태를 관리하는 GitOps 기반 CD 도구다.

```text
Git 저장소의 Kubernetes YAML
              ↓
       ArgoCD가 변경 감지
              ↓
Git의 원하는 상태와 Cluster의 실제 상태 비교
              ↓
           동기화
              ↓
Kubernetes가 Pod 생성·수정·삭제
```

ArgoCD가 애플리케이션 코드를 컴파일하거나 Docker Image를 만드는 것은 아니다.

ArgoCD의 핵심 역할은 Git에 선언한 Kubernetes 자원을 Cluster에 반영하고, 두 상태의 차이를 보여주는 것이다.

---

## CD란

CD는 문맥에 따라 다음 두 의미로 사용된다.

| 용어 | 의미 |
|---|---|
| Continuous Delivery | 언제든 배포할 수 있는 상태까지 자동화하고 실제 배포는 승인할 수 있음 |
| Continuous Deployment | 검증을 통과한 변경을 운영 환경까지 자동 배포 |

현재 프로젝트에서 GitHub Actions는 코드 검사와 Image 생성을 담당하고, ArgoCD는 Git에 기록된 Kubernetes 배포 상태를 Cluster에 반영한다.

---

## GitOps란

GitOps는 Git 저장소를 시스템의 원하는 상태를 기록하는 기준으로 사용하는 운영 방식이다.

```text
원하는 상태:
k8s/chat-deployment.yaml에 replicas: 3

실제 상태:
Cluster의 Deployment replicas: 2

ArgoCD:
두 상태가 다르다는 것을 감지
```

GitOps의 핵심:

- Kubernetes 설정을 Git에 선언한다.
- 변경 이력이 Commit으로 남는다.
- Pull Request와 Review로 변경을 검토할 수 있다.
- Git 상태와 Cluster 상태의 차이를 확인한다.
- 승인된 Git 변경을 자동 또는 수동으로 동기화한다.

Git이 단순한 파일 보관 장소가 아니라 배포 상태의 기준이 된다.

---

## 현재 프로젝트의 전체 배포 흐름

```text
개발자가 Go Code 수정
        ↓
Git Push
        ↓
GitHub Actions
  - Test
  - Build
  - Docker Image 생성
        ↓
GHCR
  - Image 저장
        ↓
Git의 Kubernetes YAML
  - 배포 Image Tag 기록
        ↓
ArgoCD
  - Git 변경 감지
  - Cluster 상태 비교
  - Sync
        ↓
Kubernetes
  - Rolling Update
  - Pod 상태 유지
```

역할을 구분하면 다음과 같다.

| 구성요소 | 역할 |
|---|---|
| GitHub | Source Code와 Kubernetes Manifest 저장 |
| GitHub Actions | CI, Test, Build, Image Push |
| GHCR | Docker Image 저장 |
| ArgoCD | Git과 Cluster 비교 및 배포 동기화 |
| Kubernetes | Pod를 실제로 생성하고 실행 |

## ArgoCD가 필요한 이유

### 배포 상태를 Git에 기록

직접 다음 명령을 실행해도 Kubernetes 자원을 배포할 수 있다.

```bash
kubectl apply -f k8s/
```

하지만 수동 배포만 반복하면 다음 문제가 생길 수 있다.

- 누가 어떤 Manifest를 적용했는지 추적하기 어려움
- Git과 실제 Cluster가 서로 다른 상태가 될 수 있음
- 다른 사람이 같은 환경을 재현하기 어려움
- 변경 Review 없이 운영 상태가 바뀔 수 있음

ArgoCD를 사용하면 배포 변경이 Git Commit으로 남는다.

### 원하는 상태와 실제 상태 비교

ArgoCD는 다음 두 상태를 지속적으로 비교한다.

```text
Desired State: Git에 기록된 Kubernetes Manifest
Live State:    Cluster에 실제로 존재하는 Kubernetes 자원
```

두 상태가 같으면 `Synced`, 다르면 `OutOfSync`로 표시한다.

### 시각적인 배포 상태 확인

ArgoCD UI에서는 Application 아래의 자원 관계를 확인할 수 있다.

```text
Application
├── Namespace
├── Deployment
│   └── ReplicaSet
│       └── Pod
├── Service
├── Ingress
├── ConfigMap
├── StatefulSet
└── HPA
```

Pod가 생성 중인지, 배포가 실패했는지, 어떤 자원이 Git과 다른지 확인하기 쉽다.

### 복구와 재현

배포 설정이 Git에 있으므로 새로운 Cluster에서도 같은 Manifest를 적용할 수 있다.

문제가 있는 변경은 이전 Git Commit을 기준으로 되돌릴 수 있다.

## Push 방식과 Pull 방식

### 일반적인 Push 배포

```text
CI Server
  ↓ kubectl apply
Kubernetes Cluster
```

CI Server가 Cluster 인증정보를 가지고 Cluster로 직접 배포 명령을 보낸다.

### ArgoCD의 Pull 방식

```text
Git Repository
      ↑ 확인
Cluster 내부 ArgoCD
      ↓ 적용
Kubernetes API
```

ArgoCD가 Cluster 안에서 Git을 확인하고 필요한 변경을 적용한다.

이 방식에서는 CI가 직접 Cluster에 접속해 배포하지 않아도 된다.

---

## Application이란

ArgoCD의 `Application`은 어떤 Git 저장소의 어떤 경로를 어느 Kubernetes Cluster와 Namespace에 배포할지 정의하는 자원이다.

현재 파일:

```text
argocd/chat-application.yaml
```

개념 구조:

```yaml
spec:
  source:
    repoURL: Git 저장소 주소
    targetRevision: 추적할 Branch
    path: Kubernetes Manifest 경로
  destination:
    server: 배포할 Cluster
    namespace: 배포할 Namespace
```

즉 다음 연결 관계를 정의한다.

```text
GitHub Repository의 k8s 폴더
              ↓
Minikube Cluster의 chat Namespace
```

## Sync와 Health

ArgoCD 화면에는 주로 Sync 상태와 Health 상태가 표시된다.

### Sync 상태

| 상태 | 의미 |
|---|---|
| `Synced` | Git의 Manifest와 Cluster 자원이 일치 |
| `OutOfSync` | Git과 Cluster 상태가 다름 |
| `Unknown` | 상태를 정상적으로 비교하지 못함 |

### Health 상태

| 상태 | 의미 |
|---|---|
| `Healthy` | 자원이 정상 상태 |
| `Progressing` | 배포 또는 변경 진행 중 |
| `Degraded` | 일부 자원이 비정상 |
| `Missing` | 필요한 자원이 없음 |
| `Suspended` | 자원 동작이 일시 중지됨 |

`Synced`와 `Healthy`는 서로 다른 의미다.

```text
Synced + Degraded
= Git 설정은 적용됐지만 애플리케이션이 정상 실행되지 않음

OutOfSync + Healthy
= 현재 애플리케이션은 실행 중이지만 Git과 Cluster 설정이 다름
```

## 자동 동기화

ArgoCD Application에 자동 동기화가 설정되면 Git 변경을 감지하여 Cluster에 자동 반영할 수 있다.

대표 옵션:

| 옵션 | 역할 |
|---|---|
| `automated` | Git 변경 시 자동 Sync |
| `prune` | Git에서 삭제된 자원을 Cluster에서도 제거 |
| `selfHeal` | Cluster에서 수동 변경된 값을 Git 상태로 복구 |

개념:

```text
Git에서 Deployment 변경
        ↓
ArgoCD가 OutOfSync 감지
        ↓
자동 Sync
        ↓
Kubernetes Rolling Update
```

`prune`은 실제 Kubernetes 자원을 삭제할 수 있으므로 Git에서 Manifest를 제거할 때 영향을 반드시 확인해야 한다.

---

## Drift와 Self Heal

Drift는 Git에 기록된 상태와 실제 Cluster 상태가 달라진 상황이다.

예:

```bash
kubectl scale deployment/chat-app --replicas=5 -n chat
```

Git에는 3개, Cluster에는 5개가 되면 Drift가 발생한다.

ArgoCD는 이를 `OutOfSync`로 감지한다.

`selfHeal`이 활성화되어 있으면 Git의 선언 상태로 되돌릴 수 있다.

단, HPA가 관리하는 `replicas`처럼 다른 Controller가 의도적으로 변경하는 필드는 충돌하지 않도록 Manifest와 관리 정책을 설계해야 한다.

---

## ArgoCD와 HPA의 관계

HPA는 부하에 따라 Deployment의 실제 Replica 수를 변경한다.

```text
CPU 증가
  ↓
HPA가 replicas 3 → 6
```

ArgoCD가 Deployment의 `replicas: 3`을 계속 강제로 적용하면 HPA와 충돌할 수 있다.

HPA가 Replica 수를 관리하는 Deployment에서는 일반적으로 Git Manifest의 고정 `replicas` 관리 여부를 신중하게 결정한다.

현재 프로젝트에서는 다음 역할을 구분한다.

```text
ArgoCD: HPA 자원과 Deployment 설정 배포
HPA:    실행 중인 Deployment Replica 수 자동 조절
```

## 주요 ArgoCD 구성요소

| 구성요소 | 역할 |
|---|---|
| `argocd-server` | Web UI, API와 CLI 요청 처리 |
| `application-controller` | Git의 원하는 상태와 Cluster 상태 비교·동기화 |
| `repo-server` | Git 저장소에서 Manifest를 가져오고 생성 |
| `applicationset-controller` | 여러 Application을 규칙에 따라 생성 |
| `dex-server` | 외부 인증 연동 |
| Redis | ArgoCD 내부 Cache와 임시 데이터 활용 |

현재 학습 환경은 단일 Minikube Cluster이므로 Non-HA 방식으로 설치하였다.

## ArgoCD가 하지 않는 일

ArgoCD의 역할을 과도하게 넓게 이해하면 안 된다.

ArgoCD는 기본적으로 다음 작업을 직접 담당하지 않는다.

- Go Source Code Test
- Go Binary Build
- Docker Image Build
- GHCR Image Push
- 애플리케이션 내부 오류 수정
- Database Backup
- Kubernetes Node 장애 복구

이 작업들은 각각 GitHub Actions, Docker Build 도구, Registry, Application, Database 운영 도구와 Kubernetes가 담당한다.

## 현재 프로젝트에서 얻는 효과

```text
배포 설정이 Git에 남음
변경 이력을 Commit으로 추적
Git과 Cluster 상태 차이 확인
Kubernetes YAML 자동 적용
Rolling Update 상태 시각화
문제가 발생한 자원 빠르게 확인
동일한 설정으로 환경 재현 가능
```

## 핵심 정리

```text
ArgoCD는 GitOps 방식으로 Kubernetes 배포 상태를 관리하는 CD 도구다.
Git의 Manifest가 원하는 상태이고 Cluster 자원이 실제 상태다.
ArgoCD는 두 상태를 비교하여 Synced 또는 OutOfSync로 표시한다.
GitHub Actions는 Test와 Image Build를 담당하고 ArgoCD는 Kubernetes 배포를 담당한다.
Kubernetes는 ArgoCD가 적용한 설정에 따라 실제 Pod를 실행한다.
```

# kubectl 조회와 장애 확인

## kubectl 기본 형식

```text
kubectl [동작] [자원 종류] [자원 이름] -n [Namespace]
```

예시:

```bash
kubectl get pvc postgres-data -n chat
```

```text
동작: get
자원 종류: pvc
자원 이름: postgres-data
Namespace: chat
```

자원 이름을 생략하면 해당 종류를 모두 조회한다.

```bash
kubectl get pvc -n chat
kubectl get service -n chat
kubectl get pods -n chat
```

---

## get, describe, logs 차이

| 명령 | 목적 |
|---|---|
| `get` | 목록과 현재 상태를 빠르게 확인 |
| `describe` | 특정 자원의 상세 설정, 연결 관계와 Events 확인 |
| `logs` | 컨테이너 애플리케이션이 출력한 로그 확인 |

```bash
kubectl get pods -n chat
kubectl describe pod postgres-0 -n chat
kubectl logs postgres-0 -n chat
```

`describe`는 자원을 수정하지 않는 조회 명령이다.

## Namespace 조회 주의사항

다음 명령은 Namespace 자체만 보여준다.

```bash
kubectl get namespace chat
```

`chat` 내부의 Pod를 조회하려면 `-n chat`을 사용한다.

```bash
kubectl get pods -n chat
```

다음 명령은 `chat`을 Namespace가 아니라 Pod 이름으로 해석하므로 잘못된 명령이다.

```bash
kubectl get pods chat
```

Namespace를 생략하면 현재 Context의 기본 Namespace인 `default`를 조회한다.

```bash
kubectl get pods
```

전체 Namespace의 Pod를 확인하려면:

```bash
kubectl get pods --all-namespaces
kubectl get pods -A
```

## 여러 자원 확인

주요 실행 자원:

```bash
kubectl get all -n chat
```

`all`이라는 이름과 달리 Secret, ConfigMap, PVC까지 모두 포함하지는 않는다.

```bash
kubectl get all,configmap,secret,pvc -n chat
```

Namespace 안에 실제로 존재하는 모든 종류의 자원을 찾으려면:

```bash
kubectl api-resources --verbs=list --namespaced -o name \
  | xargs -n 1 kubectl get --ignore-not-found -n chat -o name
```

Kubernetes가 지원하는 자원 종류와 단축어 확인:

```bash
kubectl api-resources
```

예시:

```text
pods                       po
services                   svc
persistentvolumeclaims     pvc
namespaces                 ns
```

## PostgreSQL 상태 확인

```bash
kubectl get statefulset,pod -n chat
kubectl get pvc -n chat
kubectl get service -n chat
```

Service가 Pod를 찾았는지 확인:

```bash
kubectl get endpointslice -n chat \
  -l kubernetes.io/service-name=postgres
```

PostgreSQL 최근 로그:

```bash
kubectl logs postgres-0 -n chat --tail=30
```

정상 로그 예시:

```text
database system is ready to accept connections
```

## Pending 확인

`Pending`은 Pod가 아직 Node에서 실행되지 못한 상태다.

```bash
kubectl describe pod <Pod이름> -n chat
```

맨 아래 `Events`에서 다음 원인을 확인할 수 있다.

```text
FailedScheduling
Insufficient cpu
Insufficient memory
pod has unbound immediate PersistentVolumeClaims
```

대표 원인:

- CPU 또는 메모리 부족
- PVC가 PV와 연결되지 않음
- 조건에 맞는 Node가 없음
- Scheduling 조건 불일치

컨테이너가 시작되기 전이라면 애플리케이션 로그가 없을 수 있다.

## CrashLoopBackOff 확인

`CrashLoopBackOff`는 컨테이너가 실행된 뒤 오류로 종료되고, Kubernetes가 재시작을 반복하면서 다음 재시작을 기다리는 상태다.

```text
컨테이너 시작
→ 오류로 종료
→ Kubernetes 재시작
→ 다시 오류
→ 재시작 대기 시간 증가
```

확인 순서:

```bash
kubectl get pods -n chat
kubectl describe pod <Pod이름> -n chat
kubectl logs <Pod이름> -n chat
kubectl logs <Pod이름> -n chat --previous
```

`describe`의 Events에는 재시작 상황이 표시될 수 있다.

```text
Back-off restarting failed container
```

프로그램이 실제로 종료된 원인은 `logs`에서 확인한다. `--previous`는 재시작되기 직전 컨테이너의 로그를 보여준다.

## 최근 Events 확인

```bash
kubectl get events -n chat \
  --sort-by=.metadata.creationTimestamp
```

Events는 Scheduling, 이미지 다운로드, Volume 연결, Probe 실패와 같은 Kubernetes 동작을 시간순으로 확인할 때 사용한다.

---

## 기본 장애 확인 순서

```text
1. kubectl get pods -n chat
   → 현재 상태 확인

2. kubectl describe pod <Pod이름> -n chat
   → 상태, 설정, Events 확인

3. kubectl logs <Pod이름> -n chat
   → 현재 컨테이너 로그 확인

4. kubectl logs <Pod이름> -n chat --previous
   → 직전에 종료된 컨테이너 로그 확인

5. kubectl get events -n chat --sort-by=.metadata.creationTimestamp
   → Namespace 전체의 최근 Kubernetes 이벤트 확인
```

## 로컬 이미지 방식의 한계

처음에는 Ubuntu Docker에서 이미지를 빌드한 뒤 Minikube에 직접 전달하였다.

```bash
docker build -f docker/Dockerfile -t chat-app:local app
minikube image load chat-app:local
```

이 방식은 매번 서버에 접속해 이미지를 빌드하거나 전달해야 하며, 동일한 태그를 재사용하면 이전 이미지가 실행될 수 있다.

CI 구축 후에는 GitHub Actions가 이미지를 빌드하여 GHCR에 저장하도록 변경하였다.

```text
Git Push
→ GitHub Actions 검사
→ Docker 이미지 빌드
→ GHCR Push
→ Kubernetes가 GHCR에서 Pull
```

## 커밋 SHA 이미지

배포에 사용한 이미지:

```text
ghcr.io/pang-4/chat-app:8dd58c79cb5bda5bb63bc833a597f4612b8b64aa
```

커밋 SHA 태그를 사용하면 소스 코드와 Docker 이미지의 관계가 명확하다.

```text
Git Commit 8dd58c79...
= GHCR Image 8dd58c79...
= Kubernetes에 배포된 버전
```

`latest`만 사용하면 같은 태그의 내용이 바뀌어 실제 배포 버전을 추적하기 어렵다.

## Kubernetes YAML 변경

`k8s/chat-deployment.yaml`:

```yaml
image: ghcr.io/pang-4/chat-app:8dd58c79cb5bda5bb63bc833a597f4612b8b64aa
imagePullPolicy: IfNotPresent
```

고유한 SHA 태그이므로 Node에 해당 이미지가 없다면 GHCR에서 내려받고, 이미 존재하면 같은 이미지를 재사용한다.

적용:

```bash
kubectl apply -f k8s/chat-deployment.yaml
```

## Rolling Update 과정

```bash
kubectl get pods \
  -n chat \
  -l app=chat-app \
  -w
```

관찰한 과정:

```text
새 Pod 생성
→ ContainerCreating
→ Running
→ Readiness Probe 성공
→ 기존 Pod Terminating
→ 다음 새 Pod 생성
```

Kubernetes는 새 Pod가 준비되기 전까지 기존 Pod를 유지하였다. 새 이미지 다운로드에 실패했을 때도 기존 Pod 세 개가 계속 실행되어 서비스 전체 중단을 방지하였다.

최종 확인:

```bash
kubectl rollout status deployment/chat-app \
  -n chat \
  --timeout=120s
```

```text
deployment "chat-app" successfully rolled out
```

실행 이미지 확인:

```bash
kubectl get pods \
  -n chat \
  -l app=chat-app \
  -o custom-columns='NAME:.metadata.name,IMAGE:.spec.containers[0].image,READY:.status.containerStatuses[0].ready'
```

세 Pod 모두 동일한 GHCR SHA 이미지와 `READY=true` 상태를 확인하였다.

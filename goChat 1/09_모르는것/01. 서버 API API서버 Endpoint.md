# 서버, API, API 서버, Endpoint

## 서버란?

서버는 단순히 실행 중인 모든 프로그램을 뜻하지 않는다.

> 다른 Client의 요청을 기다리고, 요청이 들어오면 데이터나 기능을 제공하는 실행 중인 프로그램을 서버라고 한다.

```text
Client
→ 기능 또는 데이터 요청
→ Server
→ 요청 처리
→ 결과 응답
```

네 프로젝트에서는 다음과 같이 구분할 수 있다.

```text
Ubuntu 미니 PC
= 서버 프로그램들이 실행되는 서버 컴퓨터

Go 채팅 프로그램
= WebSocket 요청을 처리하는 애플리케이션 서버

PostgreSQL
= 데이터 저장과 조회 요청을 처리하는 DB 서버
```

Go 채팅 서버는 Bruno와 k6의 요청을 받으므로 Server 역할을 하고, PostgreSQL에 저장 요청을 보낼 때는 Client 역할도 한다.

---

## API란?

API는 다른 프로그램이 어떤 기능을 사용할 수 있도록 공개한 사용 방법과 규칙이다.

```text
어디로 요청하는가?
어떤 데이터를 보내는가?
어떤 기능이 실행되는가?
어떤 형식으로 응답하는가?
오류는 어떻게 알려주는가?
```

네 WebSocket 채팅 API에는 다음과 같은 규칙이 있다.

```text
연결 주소: /ws
메시지 형식: JSON
메시지 종류: join, chat 등
```

```json
{
  "type": "chat",
  "sender": "",
  "content": "안녕하세요"
}
```

API는 반드시 네트워크 서버만을 의미하지 않는다. Go 패키지가 공개한 함수도 API가 될 수 있다.

```go
json.Marshal(data)
```

하지만 개발 현장에서 단순히 API라고 말하면 문맥에 따라 HTTP나 WebSocket으로 사용하는 Web API를 의미하는 경우가 많다.

## API 서버란?

API 서버는 Client가 API 규칙에 맞춰 요청하면 그 요청을 처리하고 결과를 응답하는 서버 프로그램이다.

```text
Bruno 또는 k6
→ /ws로 요청
→ Go API 서버
→ 입력 검사
→ 채팅 처리
→ PostgreSQL 저장
→ WebSocket 메시지 전송
```

Ubuntu에서 다음 명령을 실행했을 때 Go 프로그램이 API 서버로 동작하기 시작한다.

```bash
go run ./cmd/server
```

```text
server started
address=:8080
```

이 상태는 Go 프로그램이 8080번 포트에서 Client 요청을 기다린다는 의미다.

Docker나 Kubernetes를 사용해도 서버의 역할은 동일하다.

```text
직접 실행
→ Ubuntu에서 Go API 서버 실행

Docker
→ Container 안에서 Go API 서버 실행

Kubernetes
→ Pod 안에서 Go API 서버 실행
```

## Endpoint란?

Endpoint는 API가 제공하는 특정 기능에 접근하기 위한 주소다.

HTTP API에서는 더 정확하게 Method와 Path의 조합으로 구분한다.

```text
GET /users
→ 사용자 목록 조회 Endpoint

POST /users
→ 사용자 생성 Endpoint
```

경로가 `/users`로 같아도 Method가 다르면 서로 다른 기능이므로 다른 Endpoint다.

네 채팅 서버의 예시는 다음과 같다.

```text
GET /health/live
→ 서버 생존 확인

GET /health/ready
→ 요청 처리 준비 확인

GET /status
→ 채팅 서버 상태 조회

WS /ws
→ WebSocket 채팅 연결
```

Endpoint는 API에 도착하기 전의 별도 프로그램이 아니라 API를 구성하는 접근 지점이다.

## Router와 Handler

Client가 Endpoint로 요청하면 Router가 요청을 처리할 Handler를 선택한다.

```text
Client 요청
→ Go 서버의 8080 포트
→ Router가 Method와 Path 확인
→ 연결된 Handler 선택
→ 기능 처리
→ 결과 응답
```

예를 들어:

```text
GET /status
→ Router
→ Status Handler
→ 서버 상태 응답
```

```text
WS /ws
→ Router
→ WebSocket Handler
→ 연결 유지와 채팅 처리
```

주소만 있고 처리할 Handler가 연결되어 있지 않으면 정상적인 API Endpoint가 아니며 일반적으로 `404 Not Found`가 반환된다.

```text
Endpoint
+ 요청을 처리하는 Handler
+ 요청·응답 규칙
= 외부에서 사용할 수 있는 API 기능
```

## CRUD와 API

CRUD는 데이터의 기본 작업을 의미한다.

```text
Create → 생성
Read   → 조회
Update → 수정
Delete → 삭제
```

CRUD 기능을 외부에서 사용할 수 있도록 Endpoint와 규칙으로 공개하면 API가 된다.

```text
POST   /users      → 회원 생성 API
GET    /users/10   → 회원 조회 API
PATCH  /users/10   → 회원 수정 API
DELETE /users/10   → 회원 삭제 API
```

서버 내부에 함수만 존재하면 내부 기능이며, Endpoint와 Handler를 통해 Client가 호출할 수 있게 공개하면 Web API 기능이 된다.

## 공공데이터 API와 API Key

공공데이터 제공기관은 API 서버와 사용 규칙을 미리 만들어 놓는다.

```text
공공데이터 API 서버
├── Endpoint
├── 요청값 규칙
├── 응답 형식
└── API Key 확인
```

개발자는 문서에 적힌 규칙대로 Endpoint를 호출하고 발급받은 API Key를 함께 전송한다.

```text
GET /weather?region=서울&serviceKey=발급받은키
```

API Key는 API 자체가 아니라 등록된 사용자인지 확인하고 요청량을 관리하기 위한 출입증과 같은 값이다. 실제 API Key는 GitHub에 올리지 않고 환경변수나 Secret으로 관리한다.

## Go API 서버와 Kubernetes API Server

두 서버는 이름은 비슷하지만 역할이 다르다.

| 구분 | Go 채팅 API 서버 | Kubernetes API Server |
|---|---|---|
| 요청하는 Client | Bruno, k6, 채팅 사용자 | kubectl, ArgoCD, kubelet 등 |
| 관리 대상 | WebSocket 연결과 채팅 | Pod, Deployment, Service 등 |
| 목적 | 채팅 기능 제공 | Kubernetes Cluster 관리 요청 처리 |

```text
채팅 사용
Bruno/k6
→ Go API 서버
→ 채팅 처리
```

```text
Kubernetes 관리
kubectl/ArgoCD
→ Kubernetes API Server
→ Pod와 Service 관리
```

Kubernetes API Server는 클러스터 관리 요청의 중앙 통로지만, 실제 Pod 배치와 실행은 Scheduler, Controller와 kubelet이 역할을 나누어 수행한다.

## 최종 정리

```text
Server
= 다른 Client의 요청을 기다리고 기능이나 데이터를 제공하는 프로그램

API
= 다른 프로그램이 기능을 사용할 수 있도록 공개한 사용 규칙

API Server
= API 규칙에 따라 요청을 실제로 처리하는 서버 프로그램

Endpoint
= API의 특정 기능에 접근하는 주소

Handler
= Endpoint로 들어온 요청을 실제로 처리하는 코드
```

네 프로젝트에 적용하면 다음과 같다.

```text
Go 채팅 프로그램 = API 서버
WebSocket 사용 규칙 = API
/ws = WebSocket Endpoint
WebSocket Handler = 요청 처리 코드
Bruno와 k6 = Client
```

# 각 파일의 역할

현재 프로젝트는 실행, 설정, 채팅, 데이터베이스, HTTP 서버 역할을 패키지별로 분리하였다.

```text
main
↓
application
├── config
├── database
├── chat
└── server
```

---

## `cmd/server/main.go`

Go 프로그램의 실행 진입점이다.

- JSON 형식의 Logger 생성
- `application.Run()` 호출
- 애플리케이션 실행 중 오류가 발생하면 로그를 남기고 종료

`main.go`는 세부 기능을 직접 만들지 않고 프로그램을 시작하는 역할만 담당한다.

---

## `internal/application/app.go`

애플리케이션에 필요한 구성요소를 생성하고 서로 연결한다.

실행 순서는 다음과 같다.

```text
환경변수 로드
↓
종료 신호를 처리할 Context 생성
↓
PostgreSQL 연결
↓
테이블 생성
↓
Hub 생성 및 실행
↓
Repository 생성
↓
WebSocket Handler 생성
↓
HTTP Server 생성 및 실행
```

각 패키지의 기능을 한곳에서 조립하기 때문에 `main.go`와 개별 패키지가 복잡해지는 것을 막을 수 있다.

---

# Chat 패키지

## `internal/chat/client.go`

WebSocket 연결 하나를 `Client`로 관리한다.

```go
type Client struct {
    name string
    conn *websocket.Conn
    send chan []byte
}
```

- `name`: 입장할 때 등록한 사용자 이름
- `conn`: 실제 WebSocket 연결
- `send`: Client에게 전송할 JSON 데이터를 보관하는 Buffered Channel

주요 기능은 다음과 같다.

- `readPump()`: Client가 보낸 Text Message를 계속 읽는다.
- `writePump()`: `send` Channel의 데이터를 Client에게 전송한다.
- Ping/Pong을 사용하여 연결이 살아 있는지 확인한다.
- 메시지 크기와 읽기·쓰기 시간을 제한한다.
- 연결이 끝나면 WebSocket을 닫는다.

---

## `internal/chat/handler.go`

WebSocket 연결을 시작하고 수신한 메시지를 처리한다.

주요 역할은 다음과 같다.

- 요청의 Origin 확인
- HTTP 연결을 WebSocket으로 Upgrade
- Client 생성
- `writePump()`를 Goroutine으로 실행
- Client를 Hub에 등록
- `readPump()`로 메시지 수신
- JSON을 `IncomingMessage`로 변환
- 입장 및 채팅 메시지 검증
- 채팅 메시지를 Repository에 저장
- 저장된 메시지를 Hub에 Broadcast
- 오류 메시지를 해당 Client에게만 전송
- 연결 종료 시 Hub에서 Client 제거

Handler는 WebSocket 통신의 전체 흐름을 조정하지만, Client 목록을 직접 관리하거나 SQL을 직접 실행하지 않는다.

---

## `internal/chat/hub.go`

현재 접속한 모든 Client를 관리하는 중앙 관리자이다.

Hub가 처리하는 이벤트는 다음과 같다.

- `register`: 새로운 Client 등록
- `unregister`: 연결이 종료된 Client 제거
- `broadcast`: 모든 Client에게 메시지 전달
- `direct`: 특정 Client에게만 메시지 전달

Hub는 `Run()` 안의 `select`를 사용하여 여러 Channel 이벤트를 처리한다.

각 Client의 `send` Channel이 가득 차면 해당 Client를 제거한다. 느린 Client 하나 때문에 전체 Broadcast가 멈추는 것을 방지하기 위한 처리이다.

현재 연결 수는 `atomic.Int64`로 관리하며 `/stats` API에서 사용한다.

---

## `internal/chat/message.go`

채팅에서 사용하는 메시지 형식을 정의한다.

```go
type Message struct {
    ID        int64
    Type      string
    Sender    string
    Content   string
    CreatedAt time.Time
}
```

메시지 종류는 다음과 같다.

- `join`: Client가 채팅에 입장할 때 보내는 메시지
- `chat`: 일반 채팅 메시지
- `system`: 입장과 퇴장 같은 서버 알림
- `error`: 특정 Client에게 보내는 오류 안내

클라이언트가 서버로 보내는 `IncomingMessage`와 서버가 전송하는 `Message`를 분리하였다. 서버가 관리하는 `ID`, `CreatedAt` 등의 값을 클라이언트 입력과 구분하기 위해서다.

`NewSystemMessage()`와 `NewErrorMessage()`도 이 파일에 있다. 현재 규모에서는 별도의 `message_factory.go`를 만들지 않고 메시지 정의와 생성 함수를 함께 관리한다.

---

## `internal/chat/repository.go`

채팅 메시지를 저장하는 기능을 인터페이스로 정의한다.

```go
type MessageRepository interface {
    Save(ctx context.Context, message *Message) error
}
```

Chat 패키지는 메시지가 PostgreSQL에 저장되는지 다른 저장소에 저장되는지 알 필요가 없다. `Save()` 기능만 사용하며, 실제 PostgreSQL 코드는 Database 패키지가 구현한다.

---

## `internal/chat/handler_test.go`

실제 PostgreSQL 대신 메모리에서 동작하는 가짜 Repository를 사용하여 WebSocket 채팅 흐름을 테스트한다.

- 사용자 입장
- 입장 알림 Broadcast
- 채팅 메시지 저장
- 저장된 메시지 Broadcast
- 입장 전 채팅 차단
- Sender 위조 방지

# Config 패키지

## `internal/config/config.go`

환경변수를 읽어 서버와 데이터베이스 설정을 만든다.

- 서버 주소
- 허용할 WebSocket Origin
- PostgreSQL 주소와 계정 정보
- SSL Mode
- Connection Pool 크기

로컬에서는 `.env`를 읽고, 컨테이너나 Kubernetes에서는 외부에서 주입된 환경변수를 그대로 사용한다.

---

# Database 패키지

## `internal/database/database.go`

PostgreSQL 연결을 생성하고 Connection Pool을 설정한다.

- 접속 URL 생성
- `sql.Open()`으로 `sql.DB` 생성
- 최대 연결 수와 유휴 연결 수 설정
- `PingContext()`로 실제 연결 확인

---

## `internal/database/migrate.go`

서버 시작 시 `messages` 테이블이 없으면 생성한다.

```text
PostgreSQL 연결
↓
CREATE TABLE IF NOT EXISTS
↓
messages 테이블 준비
```

현재 단계에서는 별도의 Migration Tool 없이 `ExecContext()`로 초기 테이블을 생성한다.

---

## `internal/database/message_repository.go`

`chat.MessageRepository` 인터페이스의 PostgreSQL 구현이다.

메시지를 `messages` 테이블에 저장하고 PostgreSQL이 만든 `id`와 `created_at`을 다시 Message에 담는다.

```text
Message
↓
INSERT INTO messages
↓
RETURNING id, created_at
↓
완성된 Message
```

# Server 패키지

## `internal/server/router.go`

URL과 Handler를 연결한다.

- `/ws`: WebSocket 채팅
- `/health/live`: 애플리케이션 실행 상태
- `/health/ready`: PostgreSQL을 포함한 준비 상태
- `/stats`: 현재 WebSocket 연결 수

---

## `internal/server/middleware.go`

HTTP 요청의 Method, Path, 처리 시간을 구조화 로그로 남긴다.

WebSocket은 연결이 오래 유지되므로 `/ws` 요청은 일반 HTTP 요청 로그에서 제외한다.

---

## `internal/server/server.go`

`http.Server`를 생성하고 실행한다.

- 서버 주소와 Handler 설정
- Timeout 설정
- 서버 실행 오류 감시
- 종료 신호 수신
- Graceful Shutdown

종료 신호를 받으면 진행 중인 요청을 정리할 시간을 준 뒤 안전하게 서버를 종료한다.

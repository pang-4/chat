
이 프로젝트는 단일 WebSocket 서버를 만드는 데서 끝나지 않고, 여러 서버 인스턴스로 늘어나도 채팅을 전달하고 Kubernetes에서 상태를 확인할 수 있도록 구성했다.

---

## 왜 `main.go`를 단순하게 만들었는가?

`main.go`에는 Logger 생성과 `application.Run()` 호출만 둔다. 설정, DB·Redis 연결, Handler와 서버 생성은 `application` 패키지가 담당한다.

```text
main
↓
application
↓
구성요소 생성 및 연결
```

프로그램의 진입점과 조립 과정을 분리하면 시작 순서를 한곳에서 확인하고, 각 기능은 자신의 역할에 집중할 수 있다.

---

## 왜 패키지를 역할별로 분리했는가?

- `chat`: WebSocket 채팅 규칙과 연결 관리
- `database`: PostgreSQL 연결·스키마 확인·메시지 저장
- `messaging`: Redis Pub/Sub 메시지 전달
- `server`: HTTP 경로, 메트릭, 상태 점검, 종료 처리
- `config`: 환경변수와 설정 검증
- `application`: 구성요소 조립과 실행 순서

예를 들어 채팅 규칙을 바꿀 때 Redis 연결 코드나 HTTP 서버 설정을 함께 수정할 필요가 없다.

---

## 왜 migration을 서버 시작과 분리했는가?

테이블 생성·변경은 `go run ./cmd/migrate up`으로 명시적으로 실행한다. 서버는 시작할 때 테이블을 만들지 않고 `messages` 테이블이 있는지만 확인한다.

```text
Migration 실행 → 스키마 변경
서버 실행      → 스키마 확인 후 요청 처리
```

여러 Pod가 동시에 시작할 때 각 서버가 스키마를 바꾸려 하면 실행 순서와 오류 처리가 복잡해진다. 배포 단계에서 migration을 한 번 실행하고 서버는 검증만 하도록 분리하면 책임이 명확해진다.

---

## 왜 Hub를 만들었는가?

Hub는 **한 서버 인스턴스에 연결된** Client의 등록, 해제, 전체 전송, 개별 전송, 연결 수를 한 Goroutine에서 관리한다.

```text
이 인스턴스의 Client A ─┐
이 인스턴스의 Client B ─┼─→ Hub ─→ 이 인스턴스의 Client들
이 인스턴스의 Client C ─┘
```

여러 Goroutine이 Client Map을 직접 수정하지 않고 이벤트를 Channel로 보내므로 연결 상태를 일관되게 관리할 수 있다.

---

## 왜 Redis Pub/Sub를 사용하는가?

Hub만으로는 같은 서버에 연결된 Client에게만 메시지를 보낼 수 있다. Pod가 여러 개면 Client가 서로 다른 Pod에 연결될 수 있으므로, Handler는 입장·퇴장·채팅 메시지를 Redis 채널에 발행한다.

```text
Pod A Handler → Redis 채널 → Pod A Hub
                         ├→ Pod B Hub
                         └→ Pod C Hub
```

각 Pod는 Redis를 구독하고 받은 메시지를 자기 Hub로 Broadcast한다. 이 구조로 어느 Pod에 접속했든 같은 메시지를 받을 수 있다.

Redis Pub/Sub는 실시간 전달 역할이고, 메시지 영구 보관은 PostgreSQL이 담당한다.

---

## 왜 Client와 ReadPump·WritePump를 분리했는가?

`Client`는 WebSocket 연결 하나와 검증된 사용자 이름, 전송 Queue를 묶는다.

```text
readPump  : Client → Server
writePump : Server → Client
```

읽기와 쓰기를 분리하면 양방향 통신을 동시에 처리할 수 있고, WebSocket 쓰기를 `writePump()` 한곳에서만 수행해 동시에 같은 연결에 쓰는 문제를 막는다.

---

## 왜 Message와 IncomingMessage를 분리했는가?

Client 입력은 신뢰할 수 없고, 서버가 관리할 값도 있기 때문이다.

```text
IncomingMessage: Type, Sender, Content
Message:         ID, Type, Sender, Content, CreatedAt
```

`ID`와 `CreatedAt`은 PostgreSQL·서버가 정하며, 채팅의 Sender는 Client가 보낸 값 대신 입장 때 검증해 저장한 `Client.Name`을 사용한다.

---

## 왜 Repository와 Publisher를 인터페이스로 두었는가?

Handler는 "메시지를 저장한다"와 "다른 인스턴스에 전달한다"는 기능만 알면 된다.

```text
Handler
├─ MessageRepository → PostgreSQL 구현
└─ MessagePublisher  → Redis 구현
```

구현 세부 사항과 채팅 규칙을 분리해 테스트에서는 가짜 Repository·Publisher를 넣을 수 있고, 저장소나 메시지 브로커를 바꿀 때 Handler 변경을 줄일 수 있다.

---

## 왜 저장한 뒤 Redis에 발행하는가?

채팅 메시지는 먼저 PostgreSQL에 저장하고, 성공한 메시지만 Redis에 발행한다.

```text
입력 검증
↓
PostgreSQL 저장
↓ 성공
Redis 발행
↓
각 Hub가 WebSocket 전송
```

먼저 전송한 뒤 저장에 실패하면 사용자는 메시지를 봤지만 기록은 남지 않는다. 저장 실패 시에는 전체 채널에 알리지 않고 보낸 Client에게만 오류를 전송한다.

---

## 왜 Buffered Channel과 느린 Client 제거 정책을 사용하는가?

짧은 순간에 메시지가 몰려도 전송 Queue가 잠시 흡수할 수 있도록 `send` Channel에 버퍼를 둔다.

```go
send: make(chan []byte, 256)
```

하지만 Queue가 계속 가득 찬 Client까지 기다리면 Hub 전체가 멈출 수 있다. 따라서 Queue에 넣을 수 없는 느린 Client는 제거해 다른 연결의 전송을 보호한다.

---

## 왜 Ping/Pong, Origin, Context를 사용하는가?

- Ping/Pong과 Deadline: 이미 끊긴 연결을 감지하고 정리한다.
- Origin 검사: 허용하지 않은 웹사이트에서 시작한 WebSocket 연결을 막는다.
- Context: SIGINT·SIGTERM을 Hub, HTTP 서버, Redis 구독 처리에 전달해 함께 종료한다.

---

## 왜 Live·Ready·Metrics API를 제공하는가?

`/health/live`는 프로세스가 실행 중인지, `/health/ready`는 PostgreSQL 연결·스키마·Redis까지 요청을 처리할 준비가 됐는지 확인한다.

Kubernetes는 Live 상태로 재시작 필요 여부를, Ready 상태로 트래픽을 보낼 수 있는지를 판단할 수 있다.

`/metrics`는 Prometheus 형식으로 현재 WebSocket 연결 수를 제공한다. `/stats`는 같은 연결 수를 간단한 JSON으로 제공한다.

---

## 왜 Graceful Shutdown과 구조화 로그를 사용하는가?

종료 신호를 받으면 HTTP 서버는 새 요청을 중단하고 진행 중인 요청을 정리할 시간을 가진다. Hub도 Context 취소를 받고 로컬 WebSocket 연결을 닫는다. Pod 교체 중 연결과 자원을 정리하기 위해 필요하다.

JSON 구조화 로그는 연결 수, 원격 주소, 종료 이유 같은 값을 필드로 남겨 운영 중 검색·분석하기 쉽게 한다.

---

## 왜 테스트에서 가짜 구현체를 사용하는가?

`handler_test.go`는 실제 PostgreSQL·Redis 대신 메모리 Repository와 로컬 Publisher를 사용한다. 그래서 입장, 메시지 저장, Broadcast, Sender 위조 방지 규칙을 외부 서비스 없이 빠르게 검증할 수 있다.

---

## 핵심 설계 방향

```text
역할 분리
신뢰할 수 없는 입력 검증
PostgreSQL로 메시지 보관
Redis로 여러 서버 인스턴스에 실시간 전달
느린 연결로부터 전체 서버 보호
Kubernetes가 확인할 수 있는 상태·메트릭 제공
안전한 종료와 테스트 가능한 구조
```

# 왜 이렇게 설계했을까?

현재 프로젝트의 구조는 WebSocket 채팅 기능을 구현하는 것뿐 아니라, 연결 증가와 장애 및 이후 Kubernetes 운영까지 고려하여 구성하였다.

---

## 왜 `main.go`를 단순하게 만들었는가?

`main.go`가 설정, DB 연결, Handler 생성, 서버 실행을 모두 담당하면 코드가 빠르게 복잡해진다.

현재 `main.go`는 Logger를 만들고 `application.Run()`을 호출하는 역할만 한다. 전체 구성요소를 조립하는 책임은 `application` 패키지에 둔다.

```text
main
↓
application
↓
각 구성요소 생성 및 연결
```

프로그램의 진입점과 실제 구성 과정을 분리하면 실행 흐름을 이해하고 테스트하거나 변경하기 쉬워진다.

---

## 왜 패키지를 역할별로 분리했는가?

프로젝트에는 서로 다른 역할이 있다.

- `chat`: WebSocket 채팅 규칙
- `database`: PostgreSQL 연결과 저장
- `server`: HTTP 서버와 Routing
- `config`: 환경변수와 설정
- `application`: 구성요소 조립과 실행 순서

역할을 분리하면 채팅 로직을 수정할 때 DB 연결 코드까지 함께 확인할 필요가 없고, 한 파일이 지나치게 커지는 것도 막을 수 있다.

---

## 왜 Hub를 만들었는가?

Client끼리 직접 연결하면 접속자가 많아질수록 등록, 해제, 메시지 전달을 관리하기 어렵다.

Hub가 중앙에서 다음 작업을 담당한다.

- Client 등록
- Client 해제
- 전체 Broadcast
- 특정 Client에게 개별 전송
- 현재 연결 수 관리

```text
Client A ─┐
Client B ─┼─→ Hub ─→ 모든 Client
Client C ─┘
```

Client 관리 규칙을 한곳에 모으면 동시성 문제를 줄이고 연결 상태를 일관되게 관리할 수 있다.

---

## 왜 Client를 만들었는가?

WebSocket 연결 하나를 객체처럼 관리하기 위해서다.

Client 안에는 다음 값이 있다.

- WebSocket 연결
- 서버가 검증한 사용자 이름
- 전송할 데이터를 담는 Channel

연결마다 Client 하나를 만들면 읽기, 쓰기, 연결 종료 상태를 독립적으로 관리할 수 있다.

---

## 왜 ReadPump와 WritePump를 분리했는가?

WebSocket은 메시지를 받는 동안에도 메시지를 보낼 수 있어야 한다.

```text
ReadPump  : Client → Server
WritePump : Server → Client
```

읽기와 쓰기를 분리하면 두 작업을 동시에 처리할 수 있다. `writePump()`는 별도 Goroutine에서 실행되고 `readPump()`는 현재 연결의 수신 흐름을 담당한다.

또한 하나의 WebSocket 연결에 대한 쓰기를 `writePump()` 한곳에서 처리하여 여러 Goroutine이 동시에 같은 연결에 쓰는 문제를 방지한다.

---

## 왜 Message와 IncomingMessage를 분리했는가?

Client가 서버로 보내는 값과 서버가 관리하는 값이 다르기 때문이다.

```text
IncomingMessage
- Type
- Sender
- Content

Message
- ID
- Type
- Sender
- Content
- CreatedAt
```

`ID`와 `CreatedAt`은 DB와 서버가 결정해야 한다. 두 구조체를 분리하면 Client가 보낸 값을 서버 데이터로 그대로 신뢰하는 실수를 줄일 수 있다.

채팅 Sender도 Client 입력을 그대로 사용하지 않고, 입장할 때 검증하여 저장한 `Client.Name`을 사용한다.

---

## 왜 별도의 `message_factory.go`가 없는가?

현재 생성 함수는 `NewSystemMessage()`와 `NewErrorMessage()`뿐이며 크기도 작다.

따라서 `message.go`에서 메시지 구조와 생성 규칙을 함께 보는 편이 더 단순하다. 생성 규칙이 많아지고 파일이 커지면 그때 별도 파일로 분리할 수 있다.

---

## 왜 Repository 인터페이스를 만들었는가?

Chat 패키지가 PostgreSQL의 SQL과 연결 방법까지 알지 않게 하기 위해서다.

```go
type MessageRepository interface {
    Save(ctx context.Context, message *Message) error
}
```

Handler는 `Save()`만 호출한다. 실제 저장 구현은 Database 패키지에 있다.

```text
Chat Handler
↓ MessageRepository 인터페이스
Database MessageRepository
↓
PostgreSQL
```

이 구조의 장점은 다음과 같다.

- 채팅 로직과 SQL을 분리할 수 있다.
- 테스트에서 실제 DB 대신 가짜 Repository를 사용할 수 있다.
- 저장 방식이 바뀌어도 Handler 변경을 줄일 수 있다.

---

## 왜 DB에 저장한 후 Broadcast하는가?

먼저 Broadcast하고 DB 저장에 실패하면 사용자는 메시지를 봤지만 새로 접속하거나 조회했을 때 기록이 없는 상태가 생긴다.

현재 흐름은 다음과 같다.

```text
입력 검증
↓
DB 저장
↓ 성공
Broadcast
```

저장 실패 시에는 보낸 Client에게만 오류를 전달한다. 이렇게 하면 전송된 메시지와 저장된 메시지의 상태를 일치시키기 쉽다.

---

## 왜 Channel을 버퍼로 만들었는가?

Broadcast 순간에 여러 Client에게 보낼 데이터가 몰릴 수 있다.

Buffered Channel은 일정 개수의 메시지를 잠시 대기시킬 수 있어, 짧은 처리 속도 차이 때문에 바로 전체 흐름이 막히는 것을 줄인다.

```go
send: make(chan []byte, 256)
```

하지만 버퍼는 무한하지 않다. 계속 소비하지 못하는 Client의 Queue가 가득 차면 연결을 제거한다.

---

## 왜 느린 Client를 제거하는가?

Client의 전송 Queue에 데이터를 넣을 때 기다리도록 만들면 느린 Client 하나 때문에 Hub 전체가 멈출 수 있다.

현재는 `select`의 `default`를 이용하여 기다리지 않고 전송 가능 여부를 확인한다.

```text
Queue에 공간 있음 → 메시지 추가
Queue가 가득 참   → Client 제거
```

다수의 연결을 처리하는 서버에서는 전체 서비스의 흐름을 보호하기 위한 정책이다.

---

## 왜 메시지를 Hub에 `[]byte`로 전달하는가?

같은 Broadcast 메시지를 Client마다 `json.Marshal()`하면 접속자 수만큼 같은 변환을 반복해야 한다.

Handler에서 한 번 JSON으로 변환한 뒤 Hub와 Client에는 `[]byte`로 전달한다.

```text
Message
↓ JSON 변환 1회
[]byte
↓
모든 Client에게 전달
```

---

## 왜 Ping/Pong과 Deadline을 사용하는가?

네트워크가 끊겨도 서버가 즉시 연결 종료를 알지 못하는 경우가 있다.

- 서버가 주기적으로 Ping 전송
- Client의 Pong을 받으면 Read Deadline 갱신
- 일정 시간 응답이 없으면 연결 종료
- 읽기와 쓰기에도 시간 제한 설정

응답하지 않는 연결이 Hub에 계속 남아 자원을 사용하는 것을 방지한다.

---

## 왜 Origin을 확인하는가?

브라우저의 WebSocket 요청이 허용된 웹사이트에서 시작되었는지 확인하기 위해서다.

개발 환경에서는 `*`를 사용할 수 있지만, 운영 환경에서는 실제 Frontend 주소만 허용하는 것이 안전하다. 허용 목록은 코드에 고정하지 않고 환경변수로 설정한다.

---

## 왜 Context를 사용하는가?

서버 종료 신호를 Hub, HTTP 서버, DB 작업에 전달하기 위해서다.

```text
종료 신호
↓
Context 취소
├── Hub 종료
├── HTTP 서버 종료
└── 진행 중인 DB 작업 취소 가능
```

각 기능이 같은 종료 신호를 공유하면 Goroutine과 연결을 정리하기 쉽다.

---

## 왜 Graceful Shutdown을 사용하는가?

프로세스를 즉시 종료하면 처리 중인 HTTP 요청과 WebSocket 연결이 갑자기 끊길 수 있다.

Graceful Shutdown은 종료 신호를 받은 뒤 새로운 요청을 중단하고 기존 작업을 정리할 시간을 준다. Docker와 Kubernetes에서 컨테이너가 교체될 때도 중요한 기능이다.

---

## 왜 Health Check를 Live와 Ready로 나눴는가?

두 상태의 의미가 다르기 때문이다.

- `/health/live`: Go 애플리케이션 프로세스가 실행 중인가?
- `/health/ready`: PostgreSQL 연결을 포함하여 요청을 처리할 준비가 되었는가?

Kubernetes는 Live 상태로 재시작 필요 여부를 판단하고 Ready 상태로 트래픽을 보낼 수 있는지 판단할 수 있다.

---

## 왜 구조화 로그를 사용하는가?

문자열 로그보다 Key와 Value로 구성된 로그가 검색하고 분석하기 쉽기 때문이다.

```text
event: websocket disconnected
connections: 3
remote_addr: ...
reason: send queue full
```

나중에 로그 수집 시스템을 연결할 때 JSON 로그를 필드별로 검색할 수 있다.

---

## 왜 테스트에서 가짜 Repository를 사용하는가?

WebSocket 채팅 규칙을 테스트할 때마다 실제 PostgreSQL을 실행하면 테스트가 느리고 환경의 영향을 받는다.

가짜 Repository를 사용하면 입장, 저장, Broadcast, Sender 검증 같은 채팅 로직을 빠르고 독립적으로 확인할 수 있다.

---

## 핵심 설계 방향

```text
역할 분리
신뢰할 수 없는 입력 검증
느린 연결로부터 전체 서버 보호
저장 결과와 Broadcast 상태 일치
안전한 연결 유지와 종료
테스트 가능한 구조
```

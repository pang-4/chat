# 데이터 흐름

현재 프로젝트의 흐름은 서버 시작, WebSocket 연결, 입장, 채팅, 연결 종료로 나눌 수 있다.

---

## 1. 서버 시작 흐름

```text
main.go
↓
Logger 생성
↓
application.Run()
↓
config.Load()
↓
종료 신호 Context 생성
↓
database.Open()
↓
PostgreSQL 연결 확인
↓
database.Migrate()
↓
messages 테이블 준비
↓
chat.NewHub()
↓
Hub.Run()을 Goroutine으로 실행
↓
MessageRepository 생성
↓
WebSocket Handler 생성
↓
HTTP Server 생성 및 실행
```

PostgreSQL 연결이나 테이블 준비에 실패하면 WebSocket 서버를 실행하지 않는다. 메시지를 정상적으로 저장할 수 있는 상태에서만 요청을 받기 위해서다.

---

## 2. WebSocket 연결 흐름

```text
Client
↓
GET /ws
↓
HTTP Router
↓
Handler.ServeHTTP()
↓
Origin 확인
↓
WebSocket Upgrade
↓
Client 생성
↓
writePump() Goroutine 실행
↓
Hub.Register()
↓
readPump() 실행
```

하나의 WebSocket 연결마다 하나의 `Client`가 생성된다.

- `readPump()`: Client가 서버로 보내는 메시지 담당
- `writePump()`: 서버가 Client로 보내는 메시지 담당

읽기와 쓰기를 분리하여 양방향 통신을 동시에 처리한다.

---

## 3. 사용자 입장 흐름

Client가 다음과 같은 JSON을 보낸다.

```json
{
  "type": "join",
  "sender": "pang",
  "content": ""
}
```

처리 흐름은 다음과 같다.

```text
WebSocket JSON 수신
↓
readPump()
↓
Handler.handleMessage()
↓
json.Unmarshal()
↓
IncomingMessage 생성
↓
Type이 join인지 확인
↓
이름 공백 제거 및 길이 검증
↓
Client에 이름 저장
↓
System Message 생성
↓
JSON 변환
↓
Hub.Broadcast()
↓
모든 Client의 send Channel
↓
각 Client의 writePump()
↓
WebSocket 전송
```

이미 입장한 Client가 다시 입장하거나 이름이 올바르지 않으면 오류 메시지를 해당 Client에게만 보낸다.

---

## 4. 채팅 메시지 흐름

Client가 다음과 같은 JSON을 보낸다.

```json
{
  "type": "chat",
  "content": "안녕하세요"
}
```

처리 흐름은 다음과 같다.

```text
WebSocket JSON 수신
↓
readPump()
↓
Handler.handleMessage()
↓
json.Unmarshal()
↓
입장 여부 확인
↓
메시지 공백 제거 및 길이 검증
↓
서버가 Client.Name을 Sender로 설정
↓
MessageRepository.Save()
↓
PostgreSQL INSERT
↓
id와 created_at 반환
↓
완성된 Message를 JSON으로 변환
↓
Hub.Broadcast()
↓
모든 Client의 send Channel
↓
각 Client의 writePump()
↓
WebSocket 전송
```

클라이언트가 채팅 JSON에 임의의 Sender를 넣더라도 사용하지 않는다. 입장할 때 서버에 저장한 `Client.Name`을 Sender로 사용하여 다른 사용자를 사칭하는 것을 막는다.

---

## 5. PostgreSQL 저장 흐름

```text
Handler
↓
chat.MessageRepository 인터페이스
↓
database.MessageRepository.Save()
↓
QueryRowContext()
↓
INSERT INTO messages
↓
RETURNING id, created_at
↓
Message에 결과 저장
↓
Handler로 반환
```

DB 저장이 성공한 메시지만 Broadcast한다.

저장에 실패하면 전체 Client에게 전송하지 않고 메시지를 보낸 Client에게 오류를 전달한다. 이렇게 해야 화면에는 보였지만 DB에는 존재하지 않는 메시지가 생기지 않는다.

---

## 6. Hub의 Broadcast 흐름

```text
Handler
↓
Hub.Broadcast(payload)
↓
broadcast Channel
↓
Hub.Run()의 select
↓
접속 중인 Client 순회
↓
각 Client의 send Channel에 JSON 추가
↓
writePump()
↓
WebSocket WriteMessage()
```

Client의 `send` Channel에는 이미 JSON으로 변환된 `[]byte`가 들어간다. 같은 메시지를 Client마다 다시 JSON으로 변환하지 않아도 된다.

`send` Channel이 가득 찬 느린 Client는 Hub에서 제거한다. 한 Client 때문에 전체 Broadcast가 멈추는 것을 방지하기 위해서다.

---

## 7. 오류 메시지 흐름

```text
잘못된 JSON 또는 입력값
↓
Handler.sendError()
↓
Error Message 생성
↓
JSON 변환
↓
Hub.Send(client, payload)
↓
direct Channel
↓
해당 Client의 send Channel
↓
writePump()
↓
오류를 발생시킨 Client에게만 전송
```

입력 오류는 다른 사용자에게 알릴 필요가 없으므로 Broadcast하지 않는다.

---

## 8. 연결 유지 흐름

```text
writePump의 Ticker
↓
주기적으로 Ping 전송
↓
Client가 Pong 응답
↓
readPump의 Read Deadline 갱신
```

정해진 시간 안에 Pong이 오지 않거나 읽기·쓰기에 실패하면 연결이 종료된다. 실제로 끊어진 연결이 Hub에 계속 남는 것을 방지한다.

---

## 9. Client 연결 종료 흐름

```text
WebSocket 읽기 종료 또는 오류
↓
readPump() 반환
↓
Handler의 defer 실행
↓
Hub.Unregister()
↓
Client 제거
↓
send Channel과 WebSocket 연결 종료
↓
퇴장 System Message Broadcast
```

입장을 완료한 Client만 퇴장 메시지를 Broadcast한다.

---

## 10. 서버 종료 흐름

```text
SIGINT 또는 SIGTERM 수신
↓
Context 취소
├── Hub.Run() 종료
│   └── 모든 Client 연결 정리
└── Server.Run() 종료 처리
    └── HTTP Graceful Shutdown
↓
DB 연결 종료
↓
프로그램 종료
```

서버, Hub, WebSocket, DB 연결을 순서대로 정리하여 갑작스러운 종료로 인한 자원 누수를 줄인다.

---

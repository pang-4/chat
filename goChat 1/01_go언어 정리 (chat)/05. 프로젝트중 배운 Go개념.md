
이 문서는 현재 WebSocket 채팅 서버에서 실제로 사용한 Go 개념을 코드와 연결하여 정리한 것이다. 채팅은 PostgreSQL에 저장하고 Redis Pub/Sub로 여러 서버 인스턴스에 전달한다.

---

## Struct

Struct는 여러 데이터를 하나로 묶는 사용자 정의 자료형이다.

```go
type Client struct {
    name string
    conn *websocket.Conn
    send chan []byte
}
```

프로젝트에서는 `Client`, `Hub`, `Message`, `Config`, `Server` 등을 Struct로 만들었다.

WebSocket 연결, 이름, 전송 Channel처럼 서로 관련된 값을 하나의 Client로 관리할 수 있다.

---

## Method

Method는 특정 Type에 연결된 함수이다.

```go
func (c *Client) Name() string {
    return c.name
}
```

`Client`에는 읽기, 쓰기, 연결 종료 기능이 있고 `Hub`에는 등록, 해제, Broadcast 기능이 있다.

기능을 관련 Struct의 Method로 만들면 어떤 데이터가 어떤 동작을 담당하는지 이해하기 쉽다.

---

## Pointer

Pointer는 값이 저장된 메모리 주소를 가리킨다.

```go
*Client
*Hub
*sql.DB
*Message
```

Client나 Hub를 함수마다 복사하지 않고 같은 객체를 공유하기 위해 사용한다.

```go
func (r *MessageRepository) Save(ctx context.Context, message *chat.Message) error
```

`*Message`를 전달했기 때문에 DB에서 반환된 `ID`와 `CreatedAt`을 원래 Message에 저장할 수 있다.

---

## Constructor 함수

Go에는 언어 차원의 Constructor 문법이 없지만 보통 `New...` 함수로 값을 생성한다.

```go
func NewClient(conn *websocket.Conn) *Client
func NewHub(logger *slog.Logger) *Hub
func NewHandler(...) *Handler
```

생성에 필요한 초기값과 Channel을 한곳에서 설정하여 초기화되지 않은 객체가 만들어지는 것을 줄인다.

---

## Exported와 Unexported

Go에서는 이름이 대문자로 시작하면 다른 패키지에서 접근할 수 있고, 소문자로 시작하면 같은 패키지에서만 접근할 수 있다.

```go
type Client struct {
    name string
    conn *websocket.Conn
}

func (c *Client) Name() string
```

`name`을 외부에서 직접 변경하지 못하게 하고 `Name()`으로만 읽게 한다. Client 이름을 설정하는 규칙을 Chat 패키지 안에서 관리할 수 있다.

---

## Interface

Interface는 필요한 동작의 형태를 정의한다.

```go
type MessageRepository interface {
    Save(ctx context.Context, message *Message) error
}
```

Handler는 PostgreSQL 구현이 아니라 `Save()` 기능에 의존한다.

메시지 전달도 별도 Interface로 분리했다.

```go
type MessagePublisher interface {
    Publish(ctx context.Context, message Message) error
}
```

실제 실행에서는 PostgreSQL Repository와 Redis Publisher를 사용하고, 테스트에서는 메모리 기반 가짜 Repository와 로컬 Publisher를 사용할 수 있다.

Go에서는 별도로 `implements`를 선언하지 않아도 필요한 Method를 가지고 있으면 Interface를 구현한다.

---

## Dependency Injection

필요한 객체를 내부에서 직접 생성하지 않고 외부에서 전달받는 방식이다.

```go
func NewHandler(
    hub *Hub,
    repository MessageRepository,
    publisher MessagePublisher,
    logger *slog.Logger,
    allowedOrigins []string,
) *Handler
```

Handler가 DB, Redis, Logger를 직접 만들지 않기 때문에 구성 변경과 테스트가 쉬워진다.

이 프로젝트에서는 `application.Run()`이 각 객체를 생성하고 연결한다.

---

## Pub/Sub와 Callback

Redis는 모든 서버 인스턴스가 같은 채팅 메시지를 받도록 Pub/Sub 방식으로 사용한다.

```go
func (r *Redis) Subscribe(ctx context.Context, handle func([]byte)) error
```

`Subscribe()`는 Redis에서 메시지를 받는 일을 맡고, 받은 JSON을 어떻게 처리할지는 `handle` Callback으로 넘긴다. `application.Run()`은 이 Callback에서 로컬 `Hub.Broadcast()`를 호출한다.

```text
Handler → Redis.Publish()
↓
Redis 채널
↓
Redis.Subscribe()의 Callback
↓
각 서버 인스턴스의 Hub.Broadcast()
```

이렇게 하면 Redis 통신 코드와 WebSocket Client 관리 코드를 분리할 수 있다.

---

## Goroutine

Goroutine은 함수를 다른 작업과 동시에 실행하는 Go의 실행 단위이다.

```go
go hub.Run(ctx)
go client.writePump()
```

Hub는 모든 Client의 이벤트를 계속 처리하고, 각 Client의 WritePump는 전송할 메시지를 기다린다.

Goroutine은 가볍지만 반드시 종료 조건이 필요하다. 이 프로젝트에서는 Context 취소, Channel 종료, WebSocket 오류 등을 이용해 끝낸다.

---

## Channel

Channel은 Goroutine 사이에서 값을 전달하는 통로이다.

```go
register   chan *Client
unregister chan *Client
broadcast  chan []byte
direct     chan delivery
send       chan []byte
```

Hub의 상태를 여러 Goroutine이 직접 수정하지 않고 Channel을 통해 이벤트를 전달한다.

```text
Redis 구독 Callback 또는 Handler
↓ Hub의 Channel
Hub Goroutine
↓ Client의 send Channel
Client WritePump Goroutine
```

---

## Buffered Channel

크기를 지정한 Channel은 값이 일정 개수까지 쌓여도 보내는 쪽이 바로 기다리지 않는다.

```go
make(chan []byte, 256)
```

짧은 순간 메시지가 몰려도 WritePump가 처리할 때까지 Queue에 보관할 수 있다.

버퍼가 가득 차면 무한히 기다리지 않고 느린 Client를 제거하여 Hub 전체가 멈추는 것을 방지한다.

---

## Select

`select`는 여러 Channel 작업 중 실행 가능한 것을 처리한다.

```go
select {
case <-ctx.Done():
case client := <-h.register:
case client := <-h.unregister:
case payload := <-h.broadcast:
case item := <-h.direct:
}
```

Hub는 종료, 등록, 해제, Broadcast, 개별 전송 이벤트를 한곳에서 기다린다.

`default`를 사용하면 Channel이 준비될 때까지 기다리지 않는 Non-blocking 작업도 만들 수 있다.

```go
select {
case client.send <- payload:
    return true
default:
    return false
}
```

---

## Map

Map은 Key와 Value를 저장하는 자료구조이다.

```go
clients map[*Client]struct{}
```

Hub는 접속한 Client를 Set처럼 관리한다. Go에는 별도의 Set 자료형이 없으므로 값의 크기가 0인 `struct{}`를 사용한다.

```go
h.clients[client] = struct{}{}
delete(h.clients, client)
```

---

## Callback 함수

함수를 다른 함수의 인자로 전달할 수 있다.

```go
func (c *Client) readPump(onMessage func([]byte))
```

Client는 WebSocket에서 데이터를 읽는 일만 담당하고, 읽은 데이터를 어떻게 처리할지는 Handler가 전달한 함수가 담당한다.

이를 통해 Client의 네트워크 읽기와 Handler의 메시지 규칙을 분리할 수 있다.

---

## JSON Marshal과 Unmarshal

`json.Unmarshal()`은 JSON을 Go Struct로 변환한다.

```go
var incoming IncomingMessage
err := json.Unmarshal(payload, &incoming)
```

```text
JSON []byte
↓ Unmarshal
IncomingMessage
```

`json.Marshal()`은 Go Struct를 JSON으로 변환한다. Redis Publisher는 `Message`를 JSON으로 바꾼 뒤 Redis 채널에 발행하고, Handler는 오류 메시지를 JSON으로 바꿔 특정 Client에게 보낸다.

```go
payload, err := json.Marshal(message)
```

```text
Message
↓ Marshal
JSON []byte
```

---

## Context

Context는 작업의 취소 신호, 마감 시간 등을 전달한다.

```go
ctx, stop := signal.NotifyContext(
    context.Background(),
    os.Interrupt,
    syscall.SIGTERM,
)
```

종료 신호가 오면 Context가 취소되고 Hub, HTTP 서버, Redis 구독 Goroutine이 종료 절차를 시작한다.

DB 작업에도 `QueryRowContext()`, `ExecContext()`, `PingContext()`를 사용하여 요청이나 서버가 취소되었을 때 작업을 중단할 수 있게 한다.

---

## Context Timeout

외부 작업을 무한히 기다리지 않도록 제한 시간을 설정한다.

```go
pingCtx, cancel := context.WithTimeout(ctx, 5*time.Second)
defer cancel()
```

DB 연결 확인과 HTTP 서버 종료에 Timeout을 사용한다. PostgreSQL이나 네트워크에 문제가 있어도 서버가 영원히 멈춰 있지 않게 한다.

---

## Defer

`defer`는 현재 함수가 끝나기 직전에 실행할 작업을 예약한다.

```go
defer db.Close()
defer stop()
defer cancel()
```

함수가 중간에 오류로 반환되더라도 DB 연결, Context, Timer 같은 자원을 정리할 수 있다.

Handler에서는 연결 처리를 끝낼 때 Client를 Hub에서 제거하고 퇴장 메시지를 만드는 데 사용한다.

여러 `defer`는 등록된 순서의 반대로 실행된다.

---

## Error 처리와 Wrapping

Go에서는 오류를 반환값으로 전달한다.

```go
if err != nil {
    return fmt.Errorf("insert message: %w", err)
}
```

`%w`로 기존 오류를 감싸면 어느 작업에서 실패했는지 설명을 추가하면서 원래 오류도 유지할 수 있다.

애플리케이션 내부에서는 오류를 위로 반환하고, 최종 진입점에서 로그를 남긴 뒤 종료한다.

## Blank Import

```go
_ "github.com/jackc/pgx/v5/stdlib"
```

패키지의 함수나 Type을 직접 호출하지 않지만 `init()`을 실행하여 pgx Driver를 `database/sql`에 등록하기 위해 사용한다.

그 결과 다음 코드에서 `pgx` Driver를 선택할 수 있다.

```go
sql.Open("pgx", connectionURL)
```

Migration 명령에서도 같은 방식으로 PostgreSQL용 migration Driver와 파일 기반 migration Source를 등록한다.

```go
_ "github.com/golang-migrate/migrate/v4/database/postgres"
_ "github.com/golang-migrate/migrate/v4/source/file"
```

---

## Command와 Migration

프로젝트는 실행 목적에 따라 `cmd` 아래에 독립적인 `main` 패키지를 둔다.

- `cmd/server/main.go`: WebSocket 채팅 서버 실행
- `cmd/migrate/main.go`: `up`, `down`, `version` migration 명령 실행

Migration SQL은 `migrations/`에 두며, 서버는 실행 시 테이블을 생성하지 않고 `database.CheckSchema()`로 필요한 테이블이 있는지만 검사한다. 이 분리는 여러 서버 인스턴스가 동시에 시작할 때 스키마 변경이 겹치는 일을 줄인다.

---

## `sql.DB`와 Connection Pool

`sql.DB`는 연결 하나가 아니라 DB 연결 Pool을 관리하는 객체이다.

```go
db.SetMaxOpenConns(maxOpen)
db.SetMaxIdleConns(maxIdle)
db.SetConnMaxLifetime(30 * time.Minute)
db.SetConnMaxIdleTime(5 * time.Minute)
```

- 최대 연결 수
- 대기 상태로 유지할 연결 수
- 연결의 최대 수명
- 유휴 연결 유지 시간

을 설정하여 DB 연결 자원을 관리한다.

`sql.Open()`은 설정과 Pool 객체를 준비하며, `PingContext()`로 실제 연결 가능 여부를 확인한다.

---

## HTTP Handler

Go의 HTTP Handler는 다음 Interface를 만족하는 값이다.

```go
type Handler interface {
    ServeHTTP(http.ResponseWriter, *http.Request)
}
```

Chat의 Handler가 `ServeHTTP()`를 구현했기 때문에 Router에 직접 등록할 수 있다.

```go
mux.Handle("/ws", websocketHandler)
```

---

## Middleware

Middleware는 기존 Handler를 감싸 요청 전후에 공통 동작을 추가한다.

```go
func requestLogger(logger *slog.Logger, next http.Handler) http.Handler
```

현재는 실제 Handler를 실행한 뒤 요청 처리 시간과 Method, Path를 로그로 남긴다. 장시간 연결을 유지하는 `/ws`는 일반 HTTP 요청 로그에서 제외한다.

---

## Time Ticker와 Deadline

`time.Ticker`는 일정한 주기로 신호를 보낸다.

```go
ticker := time.NewTicker(pingPeriod)
```

WritePump는 Ticker를 이용하여 WebSocket Ping을 주기적으로 전송한다.

Read Deadline과 Write Deadline은 네트워크 작업을 기다릴 최대 시간을 정한다. 응답하지 않는 연결 때문에 Goroutine이 계속 남는 것을 방지한다.

---

## Atomic

여러 Goroutine이 공유하는 숫자를 안전하게 변경하기 위해 사용한다.

```go
count atomic.Int64
```

Hub는 Client가 등록되면 `Add(1)`, 제거되면 `Add(-1)`을 호출한다. `/stats`에서는 `Load()`로 현재 연결 수를 읽는다.

---

## Mutex

Mutex는 여러 Goroutine이 같은 데이터에 동시에 접근하지 못하도록 잠근다.

```go
type fakeMessageRepository struct {
    mu       sync.Mutex
    messages []Message
}
```

현재는 테스트용 가짜 Repository의 Slice를 안전하게 수정하기 위해 사용한다.

Hub의 Client Map은 하나의 `Run()` Goroutine만 수정하도록 설계했기 때문에 별도의 Mutex를 사용하지 않는다.

---

## Signal

운영체제는 프로그램 종료 요청을 Signal로 전달한다.

- `os.Interrupt`: 터미널에서 `Ctrl+C`
- `syscall.SIGTERM`: Docker나 Kubernetes가 보내는 종료 요청

두 Signal을 Context 취소로 바꾸어 애플리케이션 전체가 같은 종료 흐름을 사용하도록 만들었다.

```text
여러 서버 인스턴스의 Hub에 같은 메시지 전달

↓

JSON과 HTTP Handler
↓
WebSocket 메시지 및 HTTP 요청 처리

↓
스키마 변경과 서버 실행 책임 분리
```

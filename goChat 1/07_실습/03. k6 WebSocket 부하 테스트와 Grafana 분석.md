# k6 WebSocket 부하 테스트와 Grafana 분석

## 실습 목표

Kubernetes에 배포한 Go WebSocket Chat Server에 k6로 동시 연결과 Message 부하를 발생시킨다.

부하가 발생하는 동안 Prometheus와 Grafana에서 다음 변화를 확인한다.

- 활성 WebSocket 연결 수
- Pod별 CPU 사용량
- Pod별 Memory 사용량
- Network 송수신량
- Packet Drop
- PostgreSQL Storage I/O

이전 k6 실습은 Application 기능과 k6 결과를 중심으로 확인하였다.

이번 실습은 Kubernetes에 배포된 Application을 대상으로 k6 결과와 Infrastructure Metric을 같은 시간대에 비교한다.

```text
Mac k6
   ↓ WebSocket 연결과 Message
Mini PC Tailscale IP
   ↓ kubectl port-forward
chat-app Service
   ↓
Chat Pod
   ├── PostgreSQL 저장
   └── Redis Pub/Sub

kubelet/cAdvisor + chat-app /metrics
   ↓
Prometheus
   ↓
Grafana
```

## Chat Service Port Forward

Mac에서 Mini PC의 Chat Service에 접근할 수 있도록 Mini PC의 Tailscale IP에 Port Forward를 연다.

```bash
kubectl port-forward \
  --address=100.126.215.15 \
  service/chat-app \
  8080:8080 \
  -n chat
```

정상 출력:

```text
Forwarding from 100.126.215.15:8080 -> 8080
```

이 Terminal은 테스트가 끝날 때까지 종료하지 않는다.

다음처럼 `127.0.0.1`에만 열면 다른 PC의 k6가 접근할 수 없다.

```text
Forwarding from 127.0.0.1:8080 -> 8080
```

Mac에서 Health Check를 실행하여 접속 경로를 먼저 확인한다.

```bash
curl -i \
  http://100.126.215.15:8080/health/live
```

`HTTP/1.1 200 OK`가 반환되어야 한다.

## 10명 동시 연결 테스트

Mac의 Project Root에서 실행한다.

```bash
k6 run \
  -e WS_URL=ws://100.126.215.15:8080/ws \
  -e VUS=10 \
  -e HOLD_SECONDS=60 \
  loadtest/websocket-load.js
```

설정:

| 항목 | 값 | 의미 |
|---|---:|---|
| VUS | 10 | 동시 WebSocket 연결 수 |
| HOLD_SECONDS | 60 | 연결 유지 시간 |
| MESSAGE_INTERVAL_MS | 1000 | 사용자별 Message 전송 간격 |

각 VU는 다음 순서로 동작한다.

```text
WebSocket 연결
→ Join Message 전송
→ 입장 Broadcast 확인
→ 1초마다 Chat Message 전송
→ 자신의 Message와 Database ID 확인
→ 60초 후 연결 종료
```

## 수신 Message가 많은 이유

현재 Chat Server는 Chat Message를 연결된 모든 Client에게 Broadcast한다.

```text
사용자 10명
×
각 사용자 약 60개 Chat 전송
= 약 600개 Chat 전송
```

각 Chat은 연결된 10명이 수신한다.

```text
약 600개 Chat
×
수신자 10명
= 약 6,000회 수신
```

따라서 다음 결과는 정상이다.

```text
송신 Message: 610개
수신 Message: 6,000개
```

송신 값에는 Join Message가 포함될 수 있다.

## CPU 변화

![[k6 테스트 중 Grafana CPU 사용량.png]]

테스트 당시 전체 Namespace 상태:

```text
CPU Request 대비 사용률: 약 3.72%
CPU Limit 대비 사용률: 약 0.372%
```

Pod별 예:

```text
chat-app: 약 0.0004~0.0012 Core
postgres: 약 0.0095 Core
redis: 약 0.0051 Core
```

PostgreSQL과 Redis가 Chat Pod보다 높은 CPU 사용량을 보였다.

Chat Message 처리 흐름:

```text
Chat Message 수신
→ PostgreSQL INSERT
→ Message ID 반환
→ Redis Pub/Sub Publish
→ WebSocket Broadcast
```

따라서 Message가 지속적으로 발생하면 PostgreSQL과 Redis의 CPU도 증가할 수 있다.

현재 사용량은 Request와 Limit에 비해 낮아 CPU 부족이나 Throttling 징후는 없었다.

## Port Forward 테스트의 제한

다음 명령은 Kubernetes Service의 외부 Load Balancer처럼 모든 Pod에 Connection을 분산하지 않는다.

```bash
kubectl port-forward \
  service/chat-app \
  8080:8080 \
  -n chat
```

`kubectl port-forward service/...`는 Service가 선택한 Pod 하나에 Port Forward를 연결한다.

따라서 이번 테스트에서는 WebSocket Connection 10개가 한 Chat Pod에 집중되었다.

Grafana에서도 특정 Chat Pod의 Memory와 Network가 다른 두 Pod보다 크게 증가하였다.

이번 테스트가 검증한 범위:

- 단일 Chat Pod의 WebSocket 10개 처리
- PostgreSQL Message 저장
- Redis Pub/Sub
- WebSocket Broadcast
- Prometheus와 Grafana Monitoring

이번 테스트만으로 검증하지 못한 범위:

- Kubernetes Service를 통한 Connection Load Balancing
- Chat Pod 3개의 균등 부하 분산
- Ingress 환경의 WebSocket Upgrade와 Session 분산

실제 Load Balancing을 검증하려면 Ingress 또는 NodePort처럼 Kubernetes Service를 통과하는 접속 경로를 구성한다.

## 50명 동시 접속 테스트

10명 테스트와 같은 접속 경로와 Message 전송 주기를 유지하고 VU만 50명으로 증가시켰다.

```bash
k6 run \
  -e WS_URL=ws://100.126.215.15:8080/ws \
  -e VUS=50 \
  -e HOLD_SECONDS=60 \
  loadtest/websocket-load.js
```

Port Forward는 그대로 특정 Chat Pod 하나에 연결되므로, 이번 테스트 역시 **단일 Chat Pod에 WebSocket 연결 50개가 집중되는 조건**이다.

### k6 실행 결과

![[k6 Kubernetes WebSocket 50명 테스트 결과.png]]

핵심 결과:

```text
Connection 성공률: 100% (50/50)
Message 전달 성공률: 100% (50/50)
전체 Check: 6,000/6,000 성공
Check 실패: 0

WebSocket 연결 시간:
  평균 42.08ms
  p95 63.16ms
  최대 71.12ms

자기 Message 전달 지연:
  평균 59.32ms
  중앙값 31ms
  p90 162ms
  p95 179ms
  최대 714ms

전송한 WebSocket Message: 3,050개
수신한 WebSocket Message: 149,863개
수신 데이터: 20MB
송신 데이터: 216kB
```

성공률과 p95 지연은 양호했지만, 최대 Message 지연이 `714ms`까지 한 번 증가했다. 평균과 p95만 보면 놓칠 수 있는 순간적인 지연이므로, VU를 더 높일 때는 p99와 최대값도 함께 관찰해야 한다.

수신 Message 수가 약 15만 개까지 증가한 이유는 Chat이 Broadcast 방식이기 때문이다. 한 사용자가 보낸 Message가 여러 접속자에게 전달되므로 접속자 수가 늘수록 전체 전달량은 단순히 5배가 아니라 훨씬 빠르게 증가한다.

### WebSocket 연결 수

![[k6 50명 테스트 WebSocket 연결 수.png]]

```promql
sum(chat_websocket_connections)
```

Graph가 `0 → 50`으로 증가하였다. 이전 10명 테스트의 봉우리와 이번 50명 테스트의 봉우리가 함께 표시되어 Application Metric이 실제 동시 연결 수를 정확히 반영하는 것도 확인하였다.

테스트가 종료되고 Prometheus가 다음 값을 수집하면 다시 `0`으로 내려간다.

### CPU

![[k6 50명 테스트 Grafana CPU 사용량.png]]

화면에서 확인한 Namespace 전체 사용률:

```text
CPU Requests 대비: 7.23%
CPU Limits 대비: 0.723%
```

WebSocket 연결이 집중된 Chat Pod의 CPU는 표본 시점에 약 `0.00565 core`, Request 대비 `5.65%`였다. PostgreSQL은 약 `0.0199 core`, Request 대비 `19.9%`로 Chat Pod보다 더 큰 CPU 변화를 보였다.

이는 연결 유지 자체보다 반복 Message 저장과 처리 과정에서 PostgreSQL 작업이 함께 증가했기 때문이다. 전체적으로는 CPU Request와 Limit에 충분한 여유가 있었다.

### Memory와 현재 Network 사용량

![[k6 50명 테스트 Grafana 메모리와 네트워크.png]]

화면에서 확인한 Namespace 전체 사용률:

```text
Memory Requests 대비: 14.1%
Memory Limits 대비: 3.54%
```

WebSocket 연결이 집중된 Chat Pod의 Memory는 약 `11.6~13.6MiB`까지 증가했고, 다른 Chat Pod는 약 `7MiB` 수준이었다. PostgreSQL은 약 `40MiB`, Redis는 약 `4MiB`였다.

특정 Chat Pod의 Memory와 Network가 다른 두 Chat Pod보다 크게 나타난 것은 Port Forward가 연결을 한 Pod에 집중시켰다는 근거다.

### Network

![[k6 50명 테스트 Grafana 네트워크 그래프.png]]

50명 테스트 시작 시 다음 항목이 동시에 증가했다.

- Chat Pod Receive/Transmit Bandwidth
- Redis Pub/Sub Traffic
- PostgreSQL Network Traffic
- 송수신 Packet Rate

Broadcast를 담당한 Chat Pod와 Redis의 Network Traffic 증가가 특히 뚜렷하다. 반면 Received/Transmitted Packet Drop은 모든 Pod에서 `0 p/s`로 유지되었다.

Grafana 화면의 `kb/s`, `kB/s` 표기는 Panel과 단위 설정에 따라 다르게 보일 수 있으므로 숫자를 비교할 때 단위도 함께 확인한다.

### PostgreSQL Storage I/O

![[k6 50명 테스트 Grafana 스토리지 IO.png]]

테스트 종료 부근에서 PostgreSQL Write 작업이 크게 증가하였다.

```text
IOPS 최대 약 45~47.3 io/s
Write Throughput 최대 약 205~217 kB/s
```

Chat Message를 PostgreSQL에 저장하기 때문에 VU와 Message 수 증가가 Storage Write 증가로 이어졌다. Chat Pod와 Redis의 Disk I/O는 거의 없었으며, 저장 계층의 주요 부하는 PostgreSQL에 집중되었다.

50명까지는 모든 기능 Check가 성공했고 CPU, Memory Limit에도 큰 여유가 있었다. 다만 다음 변화가 확인되었다.

- 연결 p95가 증가했다.
- 최대 Message 지연이 `714ms`까지 튀었다.
- Broadcast로 인해 수신 Message와 Network Traffic이 급격히 증가했다.
- PostgreSQL Write I/O가 크게 증가했다.
- Port Forward 특성상 Chat Pod 하나에 부하가 집중되었다.

따라서 현재 결과는 **단일 Chat Pod가 50개의 동시 WebSocket 연결과 해당 Message 부하를 오류 없이 처리했다**는 의미다. 아직 Cluster 전체의 최대 처리량이나 Pod 3개의 Load Balancing 성능을 검증한 것은 아니다.

## 실습 목표

Kubernetes에 배포한 Go WebSocket Chat Server에 k6로 동시 연결과 Message 부하를 발생시킨다.

부하가 발생하는 동안 Prometheus와 Grafana에서 다음 변화를 확인한다.

- 활성 WebSocket 연결 수
- Pod별 CPU 사용량
- Pod별 Memory 사용량
- Network 송수신량
- Packet Drop
- PostgreSQL Storage I/O

이전 k6 실습은 Application 기능과 k6 결과를 중심으로 확인하였다.

이번 실습은 Kubernetes에 배포된 Application을 대상으로 k6 결과와 Infrastructure Metric을 같은 시간대에 비교한다.

```text
Mac k6
   ↓ WebSocket 연결과 Message
Mini PC Tailscale IP
   ↓ kubectl port-forward
chat-app Service
   ↓
Chat Pod
   ├── PostgreSQL 저장
   └── Redis Pub/Sub

kubelet/cAdvisor + chat-app /metrics
   ↓
Prometheus
   ↓
Grafana
```

## 실습 단계별 접속 경로

이 실습에서는 검증 목적이 확장되면서 접속 경로를 세 단계로 변경하였다.

### 1단계: Chat Service 직접 Port Forward

```text
Mac k6
→ service/chat-app Port Forward
→ 특정 Chat Pod
```

명령:

```bash
kubectl port-forward \
  --address=100.126.215.15 \
  service/chat-app \
  8080:8080 \
  -n chat
```

이 경로는 Service가 선택한 Chat Pod 하나에 Port Forward Session을 연결한다.

10명과 50명 테스트에서 WebSocket 기능, PostgreSQL 저장, Redis Pub/Sub과 단일 Pod 부하를 확인하는 데 사용하였다.

### 2단계: Ingress Controller Port Forward

```text
Mac k6
→ service/ingress-nginx-controller Port Forward
→ NGINX Ingress
→ chat-app Service
→ Chat Pod 3개
```

명령:

```bash
kubectl port-forward \
  --address=100.126.215.15 \
  service/ingress-nginx-controller \
  8080:80 \
  -n ingress-nginx
```

50명과 200명 테스트에서 NGINX WebSocket Upgrade, Ingress Routing과 여러 Chat Pod로의 신규 Connection 분산을 확인하는 데 사용하였다.

### 3단계: socat과 Ingress NodePort

```text
Mac k6
→ Tailscale IP:8080
→ socat
→ Minikube IP:31673
→ NGINX Ingress
→ chat-app Service
→ Chat Pod 3~6개
```

300명 테스트에서 `kubectl port-forward`가 `broken pipe`로 끊긴 뒤 사용한 최종 경로다.

```bash
socat \
  TCP-LISTEN:8080,bind=100.126.215.15,reuseaddr,fork \
  TCP:192.168.49.2:31673
```

이 경로로 10명 사전 검증과 300명 HPA 본 테스트를 성공시켰다.

| 단계 | 접속 대상 | 사용한 테스트 | 검증 목적 |
|---|---|---|---|
| Chat Service Port Forward | 특정 Chat Pod | 10명, 50명 | Application과 단일 Pod |
| Ingress Controller Port Forward | NGINX Ingress | 50명, 200명 | Ingress와 Pod 분산 |
| socat → Ingress NodePort | Ingress NodePort | 10명 사전, 300명 | HPA와 대량 Traffic |

Ingress, Service와 Ingress Controller의 자세한 개념은 `11_Ingress/01. Ingress란 무엇이고 어떻게 적용했는가.md`에 정리하였다.

## Chat Service Port Forward

Mac에서 Mini PC의 Chat Service에 접근할 수 있도록 Mini PC의 Tailscale IP에 Port Forward를 연다.

```bash
kubectl port-forward \
  --address=100.126.215.15 \
  service/chat-app \
  8080:8080 \
  -n chat
```

정상 출력:

```text
Forwarding from 100.126.215.15:8080 -> 8080
```

이 Terminal은 테스트가 끝날 때까지 종료하지 않는다.

다음처럼 `127.0.0.1`에만 열면 다른 PC의 k6가 접근할 수 없다.

```text

```


## 10명 동시 연결 테스트

Mac의 Project Root에서 실행한다.

```bash
k6 run \
  -e WS_URL=ws://100.126.215.15:8080/ws \
  -e VUS=10 \
  -e HOLD_SECONDS=60 \
  loadtest/websocket-load.js
```

설정:

| 항목 | 값 | 의미 |
|---|---:|---|
| VUS | 10 | 동시 WebSocket 연결 수 |
| HOLD_SECONDS | 60 | 연결 유지 시간 |
| MESSAGE_INTERVAL_MS | 1000 | 사용자별 Message 전송 간격 |

각 VU는 다음 순서로 동작한다.

```text
WebSocket 연결
→ Join Message 전송
→ 입장 Broadcast 확인
→ 1초마다 Chat Message 전송
→ 자신의 Message와 Database ID 확인
→ 60초 후 연결 종료
```

## 수신 Message가 많은 이유

현재 Chat Server는 Chat Message를 연결된 모든 Client에게 Broadcast한다.

```text
사용자 10명
×
각 사용자 약 60개 Chat 전송
= 약 600개 Chat 전송
```

각 Chat은 연결된 10명이 수신한다.

```text
약 600개 Chat
×
수신자 10명
= 약 6,000회 수신
```

따라서 다음 결과는 정상이다.

```text
송신 Message: 610개
수신 Message: 6,000개
```

송신 값에는 Join Message가 포함될 수 있다.

![[k6 테스트 중 Grafana CPU 사용량.png]]

테스트 당시 전체 Namespace 상태:

```text
CPU Request 대비 사용률: 약 3.72%

```

Pod별 예:

```text
chat-app: 약 0.0004~0.0012 Core
postgres: 약 0.0095 Core
redis: 약 0.0051 Core
```

PostgreSQL과 Redis가 Chat Pod보다 높은 CPU 사용량을 보였다.

Chat Message 처리 흐름:

```text
Chat Message 수신
→ PostgreSQL INSERT
→ Message ID 반환
→ Redis Pub/Sub Publish
→ WebSocket Broadcast
```

따라서 Message가 지속적으로 발생하면 PostgreSQL과 Redis의 CPU도 증가할 수 있다.

현재 사용량은 Request와 Limit에 비해 낮아 CPU 부족이나 Throttling 징후는 없었다.

## Port Forward 테스트의 제한

다음 명령은 Kubernetes Service의 외부 Load Balancer처럼 모든 Pod에 Connection을 분산하지 않는다.

```bash
kubectl port-forward \
  service/chat-app \
  8080:8080 \
  -n chat
```

`kubectl port-forward service/...`는 Service가 선택한 Pod 하나에 Port Forward를 연결한다.

따라서 이번 테스트에서는 WebSocket Connection 10개가 한 Chat Pod에 집중되었다.

Grafana에서도 특정 Chat Pod의 Memory와 Network가 다른 두 Pod보다 크게 증가하였다.

이번 테스트가 검증한 범위:

- 단일 Chat Pod의 WebSocket 10개 처리
- PostgreSQL Message 저장
- Redis Pub/Sub
- WebSocket Broadcast
- Prometheus와 Grafana Monitoring

이번 테스트만으로 검증하지 못한 범위:

- Kubernetes Service를 통한 Connection Load Balancing
- Chat Pod 3개의 균등 부하 분산
- Ingress 환경의 WebSocket Upgrade와 Session 분산

실제 Load Balancing을 검증하려면 Ingress 또는 NodePort처럼 Kubernetes Service를 통과하는 접속 경로를 구성한다.

## 50명 동시 접속 테스트

10명 테스트와 같은 접속 경로와 Message 전송 주기를 유지하고 VU만 50명으로 증가시켰다.

```bash
k6 run \
  -e WS_URL=ws://100.126.215.15:8080/ws \
  -e VUS=50 \
  -e HOLD_SECONDS=60 \
  loadtest/websocket-load.js
```

Port Forward는 그대로 특정 Chat Pod 하나에 연결되므로, 이번 테스트 역시 **단일 Chat Pod에 WebSocket 연결 50개가 집중되는 조건**이다.

수신 Message 수가 약 15만 개까지 증가한 이유는 Chat이 Broadcast 방식이기 때문이다. 한 사용자가 보낸 Message가 여러 접속자에게 전달되므로 접속자 수가 늘수록 전체 전달량은 단순히 5배가 아니라 훨씬 빠르게 증가한다.

### Memory와 현재 Network 사용량

![[k6 50명 테스트 Grafana 메모리와 네트워크.png]]


WebSocket 연결이 집중된 Chat Pod의 Memory는 약 `11.6~13.6MiB`까지 증가했고, 다른 Chat Pod는 약 `7MiB` 수준이었다. PostgreSQL은 약 `40MiB`, Redis는 약 `4MiB`였다.

특정 Chat Pod의 Memory와 Network가 다른 두 Chat Pod보다 크게 나타난 것은 Port Forward가 연결을 한 Pod에 집중시켰다는 근거다.

### Network

![[k6 50명 테스트 Grafana 네트워크 그래프.png]]

50명 테스트 시작 시 다음 항목이 동시에 증가했다.

- Chat Pod Receive/Transmit Bandwidth
- Redis Pub/Sub Traffic
- PostgreSQL Network Traffic
- 송수신 Packet Rate

Broadcast를 담당한 Chat Pod와 Redis의 Network Traffic 증가가 특히 뚜렷하다. 반면 Received/Transmitted Packet Drop은 모든 Pod에서 `0 p/s`로 유지되었다.

Grafana 화면의 `kb/s`, `kB/s` 표기는 Panel과 단위 설정에 따라 다르게 보일 수 있으므로 숫자를 비교할 때 단위도 함께 확인한다.

### PostgreSQL Storage I/O

![[k6 50명 테스트 Grafana 스토리지 IO.png]]

테스트 종료 부근에서 PostgreSQL Write 작업이 크게 증가하였다.

```text
IOPS 최대 약 45~47.3 io/s
Write Throughput 최대 약 205~217 kB/s
```

Chat Message를 PostgreSQL에 저장하기 때문에 VU와 Message 수 증가가 Storage Write 증가로 이어졌다. Chat Pod와 Redis의 Disk I/O는 거의 없었으며, 저장 계층의 주요 부하는 PostgreSQL에 집중되었다.

## Ingress를 이용한 Kubernetes Load Balancing 실습

### 실습 목적

앞의 Port Forward 테스트에서는 WebSocket Connection이 Chat Pod 하나에 집중되었다.

이번 실습에서는 NGINX Ingress를 접속 지점으로 사용하여 다음 항목을 검증한다.

- WebSocket Upgrade가 Ingress를 통과하는가
- 새로운 WebSocket Connection이 Chat Pod 3개로 분산되는가
- 분산 상태에서 Message Broadcast와 PostgreSQL 저장이 정상 동작하는가
- 50명과 200명에서 지연과 Resource 사용량이 어떻게 달라지는가

### Ingress Controller 활성화

Mini PC에서 Minikube Ingress Addon을 활성화하였다.

```bash
minikube addons enable ingress

kubectl get pods -n ingress-nginx
```

`ingress-nginx-controller`가 `1/1 Running`인 것을 확인한 뒤 진행하였다.

### Chat Ingress 배포

`k8s/chat-ingress.yaml`을 추가하였다.

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: chat-app
  namespace: chat
  annotations:
    nginx.ingress.kubernetes.io/proxy-read-timeout: "3600"
    nginx.ingress.kubernetes.io/proxy-send-timeout: "3600"
    nginx.ingress.kubernetes.io/proxy-buffering: "off"
spec:
  ingressClassName: nginx
  rules:
    - http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: chat-app
                port:
                  name: http
```

Git Push 이후 ArgoCD가 `k8s` 폴더의 변경을 감지하여 Ingress를 자동 배포하였다.

```bash
kubectl get application chat -n argocd
kubectl get ingress -n chat
```

확인 결과:

```text
Application: Synced / Healthy
Ingress: chat-app
Class: nginx
Address: 192.168.49.2
Port: 80
```

이 변경은 Application Code나 Dockerfile을 수정한 것이 아니므로 GitHub Actions의 Image Build는 실행되지 않는다. Kubernetes Manifest 변경은 ArgoCD가 직접 반영한다.

### Ingress 접속 경로

Mac에서 Mini PC의 Minikube Ingress에 접근할 수 있도록 Mini PC에서 Ingress Controller를 Port Forward하였다.

```bash
kubectl port-forward \
  --address=100.126.215.15 \
  service/ingress-nginx-controller \
  8080:80 \
  -n ingress-nginx
```

이전에는 `service/chat-app`을 Port Forward하여 Chat Pod 하나로 바로 연결했지만, 이번에는 `service/ingress-nginx-controller`로 연결한다.

두 명령의 차이:

```text
service/chat-app
→ 선택된 Chat Pod에 직접 연결
→ Ingress를 건너뜀

service/ingress-nginx-controller
→ Ingress Controller에 연결
→ Ingress Rule과 chat-app Service를 거침
→ 신규 Connection이 여러 Chat Pod로 분산될 수 있음
```

```text
Mac k6
  → Tailscale IP:8080
  → NGINX Ingress
  → chat-app Service
  → Chat Pod 3개
```

WebSocket은 연결된 이후 같은 Pod에 유지된다. Load Balancing은 이미 연결된 Socket을 이동시키는 것이 아니라 새로운 Connection이 생성될 때 Backend Pod를 선택하는 방식이다.

### Broadcast 부하의 특징

Connection 수는 `50 → 200`으로 4배 증가했지만 수신 Message는 약 16배 증가하였다.

```text
150,358 × 약 16 ≈ 2,399,437
```

각 사용자가 Message를 보내고 그 Message가 다수의 접속자에게 전달되므로, Broadcast 전달량은 접속자 증가에 따라 대략 제곱 형태로 커질 수 있다.

따라서 단순 Connection 수뿐 아니라 다음 지표를 함께 관찰해야 한다.

- Message 지연 p95와 p99
- Chat Pod의 Network Transmit
- Redis Pub/Sub Traffic
- PostgreSQL Write IOPS
- Packet Drop
- Pod Restart와 Error Log

## HPA 부하 테스트 전 10명 사전 검증

### 실습 목적

300명 HPA 테스트를 실행하기 전에 수정한 k6 Script와 외부 접속 경로가 정상인지 10명으로 먼저 검증하였다.

이 단계의 목적은 서버의 최대 성능을 측정하는 것이 아니라 다음 항목을 확인하는 것이다.

- 10개 WebSocket Connection이 모두 생성되는가
- 각 VU가 `join` Message 이후 실제 `chat` Message를 반복 전송하는가
- 자신이 보낸 Message를 Broadcast로 다시 수신하는가
- 저장된 Message에 PostgreSQL ID가 포함되는가
- 모든 Connection이 제한 시간 전에 정상 종료되는가

### 접속 경로 변경

### 판정

10명 사전 검증에서 접속, 전송, Broadcast 수신, Database 저장 결과, 정상 종료가 모두 성공하였다.

따라서 k6 Script와 `socat → Ingress NodePort` 접속 경로가 정상임을 확인했으며, 동일한 경로로 300명 HPA 본 테스트를 진행할 수 있다.

## 300명 HPA 본 테스트

### 실습 목적

10명 사전 검증에서 확인한 Script와 접속 경로를 그대로 사용하여 다음 항목을 최종 검증하였다.

- WebSocket 사용자 300명이 점진적으로 연결되는가
- 300명이 동시에 Message를 보내고 모두 전달받는가
- CPU 사용률이 목표 70%를 넘으면 HPA가 Chat Pod를 확장하는가
- 새 Pod가 정상적으로 생성되고 Ready 상태가 되는가
- 부하 종료 후 HPA가 최소 Pod 수로 다시 축소하는가
- 대량 Network Traffic에서도 Packet Drop이나 Connection 단절이 없는가

### 테스트 전 상태

테스트 시작 전 HPA와 Pod 수를 확인하였다.

```bash
kubectl get hpa -n chat
kubectl get pods -n chat
```

시작 상태:

```text

Chat Pod: 3개
HPA 최소 Pod: 3개
HPA 최대 Pod: 6개
CPU 목표: 70%
```

Mini PC에서는 `socat`을 실행하여 Tailscale 주소를 Ingress NodePort에 연결하였다.

```bash
socat \
  TCP-LISTEN:8080,bind=100.126.215.15,reuseaddr,fork \
  TCP:192.168.49.2:31673
```

### k6 실행

Mac에서 다음 명령을 실행하였다.

```bash
k6 run \
  -e WS_URL=ws://100.126.215.15:8080/ws \
  -e VUS=300 \
  -e RAMP_SECONDS=300 \
  -e HOLD_SECONDS=300 \
  -e MESSAGE_INTERVAL_MS=1000 \
  loadtest/websocket-hpa.js
```

테스트 흐름:

### 기존 Pod와 새 Pod의 CPU 차이

부하 중 확인한 CPU Request 대비 사용률:

```text
기존 Chat Pod:
  약 182~191%

새 Chat Pod:
  약 45~48%
```

기존 WebSocket Connection은 HPA가 새 Pod를 생성하더라도 자동으로 새 Pod로 이동하지 않는다.

처음부터 연결을 많이 가지고 있던 기존 Pod가 계속 많은 Broadcast를 처리하므로 CPU가 높게 유지되었다. 새 Pod가 생성된 후 들어온 신규 Connection만 새 Pod에도 분산되어 새 Pod의 CPU가 상대적으로 낮았다.

이는 HPA 실패가 아니라 장기 연결을 유지하는 WebSocket의 특성이다.

### Scale Down 확인

테스트 종료 직후:

```text

```

CPU가 내려가도 다음 설정 때문에 즉시 Pod를 제거하지 않는다.

```yaml
scaleDown:
  stabilizationWindowSeconds: 300
```

관찰 명령:

```bash
kubectl get hpa -n chat -w
kubectl get pods -n chat -w
```

```text
→ 최소 Pod 3개 복귀 완료
```

## 최종 결과

이번 실습을 통해 다음을 검증하였다.

- Application이 `/metrics`에서 활성 WebSocket Connection을 노출한다.
- ServiceMonitor를 통해 Prometheus가 Application Metric을 수집한다.
- Grafana에서 전체 및 Pod별 Connection을 확인할 수 있다.
- Port Forward는 Connection을 단일 Chat Pod에 집중시킨다.
- NGINX Ingress는 WebSocket Upgrade를 정상 처리한다.
- Ingress를 통해 50개 Connection이 `19/14/17`로 분산되었다.
- Ingress를 통해 200개 Connection이 `68/66/66`으로 거의 균등하게 분산되었다.
- 200명에서 Connection과 Message 전달 성공률이 모두 100%였다.
- 약 240만 건의 Broadcast 수신을 처리하면서 Packet Drop이 발생하지 않았다.
- CPU와 Memory Limit에 여유가 있었고 Pod 추가 재시작도 발생하지 않았다.
- 부하 증가에 따라 연결 지연, Message 지연, Network Traffic, PostgreSQL I/O가 증가했다.
- HPA 본 테스트 전 10명 사전 검증에서 `708/708` Check와 Message 전달률 100%를 확인했다.
- `socat`을 통해 Tailscale 주소와 Ingress NodePort를 연결하여 Port Forward에 의존하지 않는 테스트 경로를 구성했다.
- 300명 HPA 테스트에서 `225,290/225,290` Check, Connection과 Message 전달 성공률 100%를 확인했다.
- HPA가 CPU 부하에 따라 Chat Pod를 `3 → 6`으로 자동 확장했다.
- 300명 테스트에서 약 2,936만 건의 Message를 수신하고 4.0GB 데이터를 처리했으며 Packet Drop은 0이었다.
- 테스트가 `300 complete / 0 interrupted`로 정상 종료되었다.

현재 구성은 실습 조건에서 WebSocket 사용자 200명을 오류 없이 처리하였다. 이는 시스템의 절대 최대 동시 사용자 수를 의미하지 않는다. 실제 운영 용량을 결정하려면 VU를 단계적으로 올리는 Stress Test, 장시간 Soak Test, 실패 지점 이후의 Recovery Test가 추가로 필요하다.

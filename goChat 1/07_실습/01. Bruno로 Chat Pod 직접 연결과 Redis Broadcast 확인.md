## 실습 목적

Chat Deployment의 Replica를 세 개로 늘린 뒤 각 사용자를 서로 다른 Pod에 직접 연결하였다.

이 실습의 목적은 Service의 Load Balancing만 확인하는 것이 아니라, Redis Pub/Sub을 통해 서로 다른 Pod의 사용자에게 메시지가 전달되는지 검증하는 것이다.

```text
Bruno 사용자 pang → Chat Pod 1
Bruno 사용자 wang → Chat Pod 2
Bruno 사용자 kim  → Chat Pod 3
```

---

## Chat Pod 이름 확인

미니 PC:

```bash
kubectl get pods \
  -n chat \
  -l app=chat-app
```

세 Pod가 모두 `1/1 Running`인지 확인하였다.

---

## 각 Pod에 직접 Port Forward

터미널 세 개를 열고 각 명령을 따로 실행한다.

터미널 1:

```bash
kubectl port-forward \
  --address=100.126.215.15 \
  pod/<CHAT_POD_1> \
  8081:8080 \
  -n chat
```

터미널 2:

```bash
kubectl port-forward \
  --address=100.126.215.15 \
  pod/<CHAT_POD_2> \
  8082:8080 \
  -n chat
```

터미널 3:

```bash
kubectl port-forward \
  --address=100.126.215.15 \
  pod/<CHAT_POD_3> \
  8083:8080 \
  -n chat
```

```text
Mac 8081 → Pod 1의 8080
Mac 8082 → Pod 2의 8080
Mac 8083 → Pod 3의 8080
```

Port Forward 명령은 실행 중인 터미널을 유지해야 한다. `Ctrl+C`로 종료하면 해당 연결도 닫힌다.

## Bruno WebSocket 연결

Bruno에서 WebSocket 요청 세 개를 만들었다.

```text
ws://100.126.215.15:8081/ws
ws://100.126.215.15:8082/ws
ws://100.126.215.15:8083/ws
```

각 요청이 `CONNECTED` 상태인지 확인하였다.

Pod 2:


## 채팅 전송

입장한 연결에서 채팅 메시지를 전송하였다.

```json
{
  "type": "chat",
  "sender": "",
  "content": "안녕안녕"
}
```

서버는 입장할 때 저장한 사용자 이름을 사용한다.

정상 수신 예:

```json
{
  "id": 3,
  "type": "chat",
  "sender": "pang",
  "content": "안녕안녕",
  "createdAt": "..."
}
```

## 확인 결과

Pod 1에서 보낸 메시지가 Pod 2와 Pod 3에 직접 연결된 Bruno 화면에도 나타났다.

```text
Pod 1이 PostgreSQL에 메시지 저장
→ 생성된 메시지 ID 확인
→ Redis chat:messages Channel에 Publish
→ Pod 1, 2, 3이 메시지 Subscribe
→ 세 Bruno 연결 모두 메시지 수신
```

이 결과로 Redis가 여러 Chat Pod 사이의 공용 실시간 메시징 계층으로 동작한다는 것을 확인하였다.

## Service Port Forward와 차이

일반 서비스 연결:

```bash
kubectl port-forward \
  --address=100.126.215.15 \
  service/chat-app \
  8080:8080 \
  -n chat
```

Service 연결은 요청을 Chat Pod 중 하나로 전달하므로 사용자가 정확히 어느 Pod에 연결됐는지 구분하기 어렵다.

직접 Pod Port Forward는 각 사용자가 서로 다른 Pod에 연결됐다는 사실을 명확하게 통제할 수 있어 Redis Cross-Pod Broadcast 검증에 사용하였다.
